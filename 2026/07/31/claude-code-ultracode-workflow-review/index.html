Claude Code ultracode workflow 實測心得：一整隊 agent 幫我寫 API 文件，值得嗎？

Claude Code 的 ultracode 模式會把任務拆給多個 subagent 並行處理，並用「對抗性驗證」確保品質。我拿一個 API 文件補寫任務實測了一輪：品質我給 8/10，但一個簡單任務就吃掉我 27% 的用量額度，而且產出仍需要另一層驗收。這篇記錄實際的運作方式、token 成本，以及它為什麼（還）無法取代我原本的多 session 工作流。

什麼是 ultracode

Claude Code 有一個 multi-agent 編排功能 dynamic workflow：Claude 針對你描述的任務寫一支編排腳本，把工作拆成多個動態規劃的 phase，每個 phase 展開多個 subagent 並行執行。ultracode 則是觸發它的方式，兩者是不同層次的概念。這篇是我第一次實際使用的心得。

依官方文件，觸發方式有三種：

  • 單次任務：在 prompt 裡包含 ultracode 關鍵字，這次任務就會以 workflow 執行；直接用自然語言說「use a workflow」也可以。順帶一提，v2.1.160 之前的觸發關鍵字叫 workflow。
  • 整個 session：下 /effort ultracode（或啟動時 claude --effort ultracode），Claude 會對每個實質任務自動規劃 workflow。
  • 內建指令：/deep-research <問題> 是內建的 workflow；自己跑過的 workflow 也可以在 /workflows 裡按 s 存成指令重複使用。

我的測試任務：讓它同步一份落後於程式碼的 API 文件——掃描 codebase、比對現有文件、補上缺漏的 endpoint。

選這個題目是刻意的：寫 API 文件價值較低，是低風險、可拆分、做壞了也沒損失的工作，適合拿來觀察新模式的能力和流程全貌。用邊緣任務試新工具，學習成本最低——不要第一次就拿核心功能去試。

實際的運作方式：17 個寫、16 個驗證

任務開始後，它自動規劃了兩個 phase：

  1. Document phase：開了 17 個 agent，分批讀 code、各自負責一段 endpoint 的文件撰寫。
  2. Verify phase：另開 16 個 agent，每個負責驗證一部分產出。

有趣的是驗證的設計。每個驗證不是「看一遍沒問題就過」，而是對抗性的跑法：再啟動 3 個小 agent 專門嘗試推翻這個產出，至少 2 個得出「無法推翻」才算通過。從執行輸出來看，行為跟這個模式一致；不過老實說，UI 計數器只顯示頂層的 33 個 agent，懷疑者是否另計、實際總數多少，我沒能從介面確認。

這套 adversarial verify 在官方文件裡只有概念性描述：獨立 agent 交叉驗證彼此的發現、對每個 claim 投票淘汰。「懷疑者專門嘗試推翻、多數決存活」的具體框架，出自 azukiazusa 對內建 /deep-research 的實作解析（見文末參考資料）——每個 claim 由 3 個獨立懷疑者投票、2/3 決：

註：這段是 azukiazusa 原始碼的簡化改寫。另外留意官方在 v2.1.196 修正了 runtime 層的錯誤處理：驗證 agent 因 rate limit 或 API 錯誤而「無法檢查」的 claim，會列為 unverified、不算作 refuted——這跟範例 prompt 裡「不確定時預設算推翻」的判準是不同層次的事，照抄設計前請分清楚。

「預設懷疑、多數決存活」的設計，跟我之前做大規模 dead code 清理時手動安排三個獨立驗證 agent 的思路一致——差別是 ultracode 把它變成內建機制。

代價與品質：27% 額度買到 8/10 的品質

這一切不是免費的：

  • 這個任務總共消耗了我 Premium seat 額度的 27%（指 /usage 裡 5 小時滾動窗口的額度）。數字是任務前後對照 /usage 用量畫面得出的，沒有精確的 token 數。依官方定價頁，Premium seat 的用量是 Standard seat 的 5 倍。假設額度按同一倍率換算，27% × 5 ≈ 1.35 個 Standard seat 的同期額度——一個 API 文件補寫任務，就吃掉超過一整個 Standard seat。
  • 消耗大的原因之一：workflow 的 subagent 預設繼承 parent agent 的 model，所以 33 個 agent 全部是用最高階的 model 在跑。要注意這只是預設值、不是建議——官方文件的 Cost 章節反而建議對不需要最強模型的 stage 指定較小的 model。換句話說，這次的成本有一部分是我沒做 model 分層優化的結果。
  • 而且這只是一個複雜度不高的文件任務。如果是需要大量驗證的大型重構，token 只會更多。

那這些 token 買到了什麼品質？我給 8/10：大部分 endpoint 補寫得正確可用，但仍有一些小錯誤——而且是連內建對抗性驗證都沒攔下來的那種。也就是說，驗證機制能把品質拉高，但不等於零錯誤，產出仍需要其他測試（或人工抽查）守門。

週邊機制的觀察：recap 讚，insight 雞肋

測試過程中還觀察到兩個輸出機制：recap 和 insight。它們跟 ultracode 本身沒有直接關係——但在多 agent 同時跑的情境下，體感差異被放得特別大：

recap（好用）：每個段落完成後，視窗下方會小結目前的工作狀態，例如：

※ recap: API 文件同步任務已完成：補了約 64 個缺漏 endpoint、修了 2 個過時條目，並開了 PR。下一步是等你決定要盯 CI，還是開工 follow-up issue（格式統一）。

多個 agent 同時在跑的時候，很容易忘記誰在做什麼、做到哪——recap 直接解決這個問題。

insight（常常多餘）：這是我對另一種行為的自稱，官方文件查不到這個名字——它會在回覆中插入「我為什麼這樣做」的說明區塊，例如解釋它刻意用 gh issue create 而不是會順便切 branch 的 skill，避免把我從目前的 PR branch 切走。判斷本身是對的，但這類內容常跟既有回覆重複，變成雜訊。

實驗的意外發現：Agent View

為了掌握多個 agent 的狀態，我順帶發現了 Claude 提供的 Agent View（claude agents）：集中管理 session 的介面，一個畫面看到各 session 的狀態（幾個在跑、幾個等輸入、幾個完成），直觀好上手。

不過要注意它的顆粒度是 session 層級：ultracode workflow 展開的那幾十個 subagent 並不會逐一顯示在 Agent View 裡，你看到的只是「跑這個 workflow 的那一個 session」；subagent 的進度得回到該 session 的 workflow 進度畫面才看得到。

真正的落差，要拿它對照我原本的工作流才看得出來。我的多 session 工作流是「中控台模式」——這是我自己設計的 AI 協作方式，不是 Claude 官方的 agent teams 功能：一個主 session 當指揮中心，其他 agent 的產出回到中控台，由它幫我總結、甚至代替我回覆其他 agent。Agent View 能「看」到所有 session 的狀態，但無法像中控台一樣總結所有 task 的內容，要代替回覆也得用特殊方式才做得到。它是個好介面，但還不足以取代中控台。

結論：ultracode workflow 可以用，但產出要驗收

回到標題的問題，我的答案是：

  • ultracode workflow 可以拿來做某些複雜任務——邊界清楚、可平行拆分、需要驗證品質的批次工作（文件補寫、大規模清理、審查類），前提是你願意為它付 token。但產出不能免驗收：這次 8/10 的品質仍有小錯誤混過了內建驗證，它的產出應該當作「高品質的草稿」，再用其他測試做最後的守門。
  • Agent View 是好介面，但取代不了中控台模式——需要跨任務統籌、頻繁人工介入決策的日常開發，主力還是我原本的工作流。
  • 所以兩者跟既有工作流是搭配關係，不是取代關係。

比起功能本身的評測，這次測試最大的收穫是偷學了它的驗證設計。「每個產出啟動獨立的懷疑者 agent 嘗試推翻、多數決存活」——至少從這次的執行輸出看，它的驗證是照這個模式跑的——這個做法不需要 ultracode 也能用：後續我在開發較複雜的功能時，也會另外啟動三個 agent 評估產出，用同樣的對抗性思路把關品質。

這也是拿邊緣任務試新工具的另一層價值：就算工具最後沒有進入你的日常工作流，它的設計思維也可能留下來，變成你自己流程的一部分。
