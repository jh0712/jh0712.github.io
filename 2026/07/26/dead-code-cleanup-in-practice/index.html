Dead Code 清理實戰：如何安全刪除一萬四千行程式碼

最近我在一個 Next.js 專案上完成了一次大規模的死程式碼清理：213 個檔案、約 -14,100 行，使用者可見行為零變更。這篇文章不談「刪了什麼」，而是聚焦在方法論——如何在不弄壞任何東西的前提下，有信心地刪掉一大片程式碼。

（實作時間：2026-07-14）

背景知識：此專案早期為了快速驗證市場，開發速度優先於程式碼品質，經過多輪快速迭代後累積了不少技術債。我是後續才加入工程團隊，先在此專案做了幾個項目的功能，對於專案有一定了解後，才開啟了這個清理。

為什麼要清理 dead code

dead code 的成本常被低估。它不只是「放著不動的行數」，而是持續產生利息的技術債：

  • 搜尋噪音：grep 一個符號時會撞到已經沒人用的 legacy 元件，誤導判斷。我們就實際發生過工程師（以及 AI coding agent）誤以為某個舊元件仍在使用而跟著修改的案例。
  • 誤用風險：專案裡留著整組「看起來可用」的舊版表單元件，新人或 AI agent 有機會 import 到舊版而非現行版本。刪掉之後，這類錯誤在編譯期就會被擋下。
  • 升級成本：未來框架大版本升級時，需要遷移、修型別、跑 codemod 的程式碼面積，跟 dead code 的量成正比。
  • Warning 疲勞：ESLint warnings 太多時，真正的新問題會淹沒在噪音裡。
  • AI 效率：在大量使用 AI coding agent 的時代，dead code 會直接墊高 agent 的 context 與 token 消耗，也讓它更容易讀到誤導性的舊程式碼而降低產出品質。

清理的四個類別

這次清理最終整理成幾個獨立的 commit，每個 commit 對應一種風險等級不同的變更類型：

  1. 未使用的 imports / 變數 / 函式（154 檔，-839 行）：依 ESLint no-unused-vars 移除約 390 個項目——未使用的 imports、賦值後從未讀取的變數、模組內從未被引用的函式、未使用的 catch bindings（改用 optional catch binding）、以及已經失效的 eslint-disable directives。
  2. 註解掉的 dead code（17 檔，-376 行）：停用的 JSX 區塊、被取代的舊 markup、註解掉的 import 與 statement。這些歷史 git 都有，不需要用註解保存。
  3. 未被任何地方引用的檔案（68 檔，-12,000+ 行）：整組 legacy 頁面、無人 import 的 barrel 元件群、未使用的 fixtures、hooks、scripts 與樣式檔。這是風險最高的一類，後面會詳述驗證流程。
  4. Review 後的行為級修正（9 檔）：常數化永遠不會更新的 useState、移除結果沒人讀取的 API 請求、移除無效的 state 更新。

依類別拆 commit 的好處是：reviewer 可以用不同的嚴格程度看不同的 commit——第 1、2 類幾乎可以掃過去，第 3、4 類值得逐檔確認。

實作方式：AI 做清理與舉證，人做最終把關

這次清理的分工是：先用 Claude Code（Fable model）做基礎驗證跟清理，結束後由它產生風險評估報告，再由人做 code review 及風險確認。

給 AI agent 的指示核心大概是這樣（文章最後有詳細的 prompt）：

用最保守的方式做代碼清理：移除目前沒用到的 code、檔案及相關註解；避開系統核心功能；feature flag 的部分一律保留。

幾個實際運作下來的心得：

  • 「最保守」要明說。AI 對「這算不算 dead code」的判斷預設會偏積極，明確要求保守之後，它會把不確定的項目列成 open question 留給人判斷，而不是直接刪。
  • 禁區用白紙黑字圈出來。feature flag、tracking、部署 config 這些「刪了不會壞 build 但會出大事」的區域，靜態驗證抓不到，必須在 prompt 裡明確列為不可觸碰。
  • 要求 AI 產出風險報告，而不是只產出 diff。人 review 一個 -14,100 行的 PR 是不現實的，但 review 一份「我刪了什麼類別、怎麼驗證的、哪裡有殘餘風險」的報告，再抽查對應的 commit，是現實的。AI 負責舉證，人負責判決——這比人直接肉眼掃 213 個檔案可靠得多。

核心方法：工具找候選，利用 AI 來放大工作效率，人來確認過程及結果

整個流程最重要的原則是：靜態分析工具只負責提出候選名單，每一筆刪除都要有獨立的驗證證據。

Step 1：用 knip 掃出候選

knip 是 JS/TS 生態系裡找 unused files / exports / dependencies 的工具。它在這個專案掃出了 350 個未引用檔案候選。

如果直接信任這個名單全刪，一定會出事。靜態分析看不到的引用包括：

  • 動態 import（尤其是 string 拼接的路徑）
  • 字串形式的引用（config、route 定義）
  • package.json scripts 直接執行的檔案
  • 測試框架 config（jest、playwright）載入的 setup 檔
  • CI pipeline 裡直接呼叫的 scripts
  • 文件裡教人執行的指令

Step 2：逐一 grep 驗證

350 個候選的處理是一個漏斗：

  1. knip 掃出 350 個未引用檔案候選。
  2. 其中近 200 個位在「架構遷移進行中」的目錄下，整批跳過不處理（原因見後文的風險對照表）。
  3. 其餘約 150 個逐一用檔名與匯出符號 cross-grep 上述所有位置。
  4. 最後只有 68 個確認真的沒有任何 live reference 才刪除。保留下來的候選中，有 8 個是因為找到了字串引用或 script 引用——這就是不能盲信工具的證明；其餘則因驗證中仍找到引用、或脈絡不明，依保守原則保留。

Step 3：刪變數時保護 side effect

刪「賦值後從未讀取的變數」有一個陷阱：右值可能有 side effect。

原則是只刪「讀取」已死的部分，不動任何可能執行的表達式，除非能證明那個呼叫本身也是無效的（例如結果存進沒人讀的 state、而請求本身沒有伺服器端作用）。

風險對照表

大規模刪除的 PR，我建議在描述裡直接放一張「風險 / 防護 / 殘餘風險」的表，讓 reviewer 不用自己腦補你想過哪些事：

風險 防護措施 殘餘風險
誤刪仍被引用的檔案 工具掃候選 → 逐一 grep 動態引用、configs、CI、docs 才刪 低。string-concat 動態 import 理論上可能漏抓，由 production build + 全站實測涵蓋
移除變數改變行為 有 side effect 的右值保留呼叫、只刪賦值；另做專門的行為稽核，重點查金流相關路徑 低
刪除中弱化測試 逐檔比對被修改的測試檔，確認 assertions 零刪除 極低
誤刪 feature flags / tracking Feature flags 全數保留；tracking events 與團隊確認後保留，並在 staging 攔截 XHR 實測發送正常 極低
高風險區域 刻意不動：靜態資產目錄、進行中架構遷移的 stub 檔案、部署 configs 無（未觸碰）

最後一列值得展開講：也就是 Step 2 漏斗裡整批跳過的那近 200 個候選——它們全部位在「架構遷移進行中」的目錄下。這些檔案現在沒人引用，是因為遷移還沒完成，不代表它們是死的。「工具說沒人用」和「可以刪」之間隔著一層對專案脈絡的理解——這類檔案我們整批跳過，另開 issue 等團隊確認遷移意向。

驗證：讓刪除變成可證明的事

清理型 PR 的說服力來自驗證的完整度：

  1. 既有系統測試全過：typecheck、lint（0 errors）、全套測試（3,600+ 通過、0 失敗）、production build。
  2. 獨立驗證：安排了三個互相獨立的 adversarial 驗證（利用 AI agent 分別從「檔案引用」「行為變更」「測試弱化」三個角度重查一次），全數通過。找三個不同的人分段 review 也能達到類似效果，重點是驗證者不能是「順著刪除者思路看一遍」，而是帶著「我要找出他刪錯的地方」的立場。
  3. 真實環境實測：在 staging 用測試帳號把主要使用者路徑全部走過一遍——登入、搜尋、核心功能流程——並且攔截 XHR 確認保留下來的 tracking events 仍然正常發送。

另外一個細節：整理 commit 歷史時採用 rebuild 的方式，最後用 git diff 驗證整理前後的 tree 是 byte-identical，再以 --force-with-lease push。歷史變乾淨了，但內容可證明一行都沒變。

三個意料之外的教訓

1. 「Temporary」的程式碼可能已經變成永久的

原計畫要移除兩個註解標記為 temporary 的 diagnostic tracking events。跟團隊確認後才發現：這組數據已經變成某個功能正確性監測的既定基礎，決議是保留並升級為永久 telemetry——要做的不是刪程式碼，而是把程式碼和文件裡所有「temporary / remove after follow-up」的註記清掉，讓標記與現實一致。

教訓：註解說它是暫時的，不代表它還是暫時的。刪 tracking 相關的任何東西之前，先問資料的使用者。

這部分也是開發以來長久的病痛，在快速迭代的專案中，很常有這種過時註解或是程式碼，這時就仰賴專案維護人員間的互相溝通及確認。

為了避免下次還有類似情況，建議做以下防範措施：

  • 定義好 temporary 的有效期限
  • 建立提醒項目提醒相關人員，避免忘記
  • 建立 routine 定期掃描程式碼，確認是否有遺留過久未更新的資訊

有了這些，就能大幅降低因人為疏失導致程式碼資訊過舊的風險。

2. 不要高估 bundle size 的收益

刪了 14,100 行，bundle 卻幾乎沒變小——因為大多數死檔案本來就沒被 import，根本不會進 bundle。清理的真正價值在維護面（搜尋噪音、誤用風險、升級成本），不在執行面。在 PR 描述裡如實陳述這點，比膨風「效能大幅提升」更能建立信任。

3. 大面積的 PR 要儘早 merge

213 個檔案的變更面積，意味著跟其他 branch 的 conflict 機率隨時間快速上升。清理型 PR 的內容本身不急，但它的「保鮮期」很短——驗證做完就該推進 merge，拖越久重驗的成本越高。

後續：用 AI routine 每週定期清理

一次性大掃除最大的問題就是「大」：積了幾年才清，驗證成本跟 review 負擔都是一次性爆發。所以清完之後，我把整套方法論固化成一個每週定期執行的 AI routine——小步清理、每週一個小 PR，讓 dead code 不再有機會積量。

後續已經持續運作了幾週，第一週還有小部分的資料沒被清理到，第二週掃描結果為 0，再做了一次大掃除後，之後維護只需每週確認 AI 分析後的小部分程式碼變動。

這個 prompt 有幾個設計重點，也是我認為讓「無人值守的定期清理」能安全運作的關鍵：

  • AI 永遠不能自行 merge。它的產出永遠是一個等人 review 的 PR，merge 的決定權在人。
  • 規模上限（單次最多刪 20 個檔案）：寧可分好幾週清完，也不要再產出一個 review 不動的巨型 PR——這正是一次性大掃除的教訓。
  • 「無事可做」是合法結果。沒東西清就不開 PR，避免 AI 為了「交差」硬找東西刪。
  • 失敗要收乾淨：執行失敗時不可留下 half-done 的 branch 或 PR，下週重來就是乾淨的起點。
  • 無論成敗都要回報。routine 最怕的是 silent failure——它悄悄失敗了三週而沒人發現，dead code 又開始積量。強制回報讓「沒消息」本身成為異常訊號。

成果總結

  • 程式碼量減少約 14,100 行，刪除 68 個未引用檔案
  • ESLint warnings 減少 22%，lint 輸出的訊噪比明顯改善
  • 使用者可見行為零變更、tracking 資料流零中斷
  • 順手修掉幾個真正的無效行為：每次 mount 都白打一次的 API 請求、造成整頁多餘 re-render 的無效 state 更新

如果你的專案也累積了多年的死程式碼，我的建議是：別手動找，讓工具（knip + ESLint）給你候選名單；別信任工具，讓 grep 和測試給你刪除的證據；別碰你不理解脈絡的區域，那些留給知道答案的人。 然後——把整套流程固化成每週的 routine，讓這是你最後一次需要「大掃除」。
