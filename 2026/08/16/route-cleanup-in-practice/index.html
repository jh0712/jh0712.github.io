Route 清理實戰：刪一條 Route 比刪一萬行 Dead Code 更難

這是上一篇 dead code 清理的續作。這次的對象是 Next.js 專案裡的 page route：2026 年 8 月執行，盤點 70 條、刪除 16 條，AI 協作使用 Claude Code（Opus 5 model）。行數比上次少一個量級，但每一條的決策成本都更高——因為 route 的「沒人用」比一般 dead code 難證明得多。這篇一樣不談刪了什麼，談方法論：怎麼判斷一條 route 能不能刪，以及靜態掃描會在哪些地方騙你。

背景：專案早期使用了現成模板快速起步，多輪迭代後累積了大量模板遺留頁面、實驗頁、被取代的舊流程頁。上一輪 dead code 清理處理掉了「沒被 import 的檔案」，但 route 是另一種生物——它們都被框架「引用」著（檔案就是路由），knip 這類工具掃不出來，需要另一套方法。

為什麼 Route ≠ Dead Code（最關鍵的認知）

一般 dead code 有個乾淨的判準：沒被引用 = 沒在用。grep 全 repo、確認零引用、刪掉、build 過，收工。

Route 沒有這種好事。一條 route 就算站內零連結，仍然可能被系統外部使用：

  • 第三方服務引用：行銷自動化平台（如 customer.io）設定的 email 連結，可能指向一條你以為沒人用的 route。
  • 其他子網域引用：別的 subdomain 上的功能會導回主站的特定 route，主站程式碼裡完全看不到。
  • 後端設定的 return URL：Stripe 的 success_url、Twilio、OAuth callback——這些寫在後端或第三方後台，前端 repo 裡 grep 不到。
  • 廣告投放的 destination URL：設定在廣告後台，程式碼裡不存在。
  • 舊分享連結與 SEO 已索引的 URL：使用者的書籤、搜尋引擎的索引，都是活的進入點。

所以 route 清理的核心命題是：**「站內零引用」只能證明站內沒人用，不能證明沒人用。**這句話決定了整套流程的形狀——靜態掃描只能給你信心的「分級」，最終每一條都需要熟悉系統的人拍板。

核心理念：AI 做搜集與舉證，人做判斷

分工和上一次清理一致，但這次人的比重更高：

  • AI 負責體力活：爬 code 盤點所有 route、反查引用、分組、用瀏覽器模擬真實使用者訪問、把證據回寫進盤點文件。
  • 人負責拍板：所有需要系統熟悉度的判斷——這條 route 是不是某個第三方在用？那個實驗結束了沒？金流 return URL 有沒有指到這裡？
  • 整體採保守路線：寧可漏刪，不要誤刪。刪掉一個少用但關鍵的入口（例如合作夥伴嵌入的頁面），代價遠高於留著一條沒用的 route。

輔助判斷的資料來源，能用就用：

  • 系統有埋 usage log 或 nginx access log，可以直接看一條 route 近期有沒有真實流量。
  • 功能迭代遺留的 route，可以靠 feature flag 的狀態判斷實作是否還會被走到。

AI 縮短搜集與驗證的時間，決策權留在熟悉系統的人身上。

流程

Step 1：盤點與分組

請 AI 列出系統所有 page route（這次是 70 條），然後以每條 route 的字面路徑反查全 repo 的 href / router.push / redirect，再對照選單定義檔與 next.config.js 的 redirects，產出一份盤點文件。

分組不是按「能不能刪」分，而是按站內靜態掃描的信心高低分：

分區 定義 意義
A 站內零引用的孤兒頁 確認成本最低，但仍要確認
B 已經是死路由（redirect 走不到、頁面被掏空），但站內還有連結指著 刪除會連帶改動使用者看得到的行為
C 已知或高度懷疑有站外進入點 逐條列出「要問誰、查哪個設定」
D 確認保留 記下為什麼保留，跟記錄刪除一樣重要

舉例說明各區長什麼樣子：

  • A 區的典型是「模板遺留」：專案當初套用現成模板起步，整組 dashboard 頁面跟著一起進了 repo。後來選單定義只保留了實際有做的四個入口，其他頁面沒有任何入口指向、站內 grep 不到任何連結，但檔案還在、route 還活著，直接打 URL 仍然進得去。
  • B 區是「已經死了但屍體還連著線」：例如一條 route 的 page 檔被掏空成 return null（使用者點進去看到整頁空白），或 next.config.js 已設 redirect、page 內的第二層 redirect 永遠執行不到——但 header 或按鈕上還有連結指著它，刪除就得連那些連結一起改。
  • C 區是「刪之前知道要去問誰」：例如疑似 A/B 實驗遺留的替代方案頁（要查 feature flag 平台上實驗結束了沒）、付款完成頁（要查金流的 return URL 設定）、內部調校工具頁（要問還在不在用）。

這個分區框架本身就經歷過一次修正：初版文件把 A 區寫成「高信心可移除」，只有 C 區標示需確認——這是錯的。修正後的前提是 A / B / C 一律要人工確認才可刪，分區只代表確認成本的高低，不代表可以跳過確認。

Step 2：讓 AI 模擬真實使用者訪問

用 browser automation（agent browser 或 Playwright）分別以已登入與未登入兩種狀態實際走訪這些 route，記錄實際行為（200 / 404 / redirect / 白畫面），回寫到盤點文件。

這一步的價值：把「這條 route 現在還通不通」變成有憑有據的紀錄，而不是憑印象猜測。後面會看到，光這一步就推翻了盤點文件裡的好幾個結論。

Step 3：每條 route 的刪除 gate

不分 A / B / C，每一條刪除前都走完這四步：

  1. 重新 rg 站內引用（含 template literal、選單定義、next.config.js redirects）——不要信任幾天前的盤點結果。
  2. 人工確認站外／第三方進入點：金流 return URL、廣告後台、合作夥伴嵌入、email 樣板、SEO 索引。這一步靜態掃描做不到。
  3. 系統負責人簽核。
  4. 刪除後跑 typecheck / lint / test / build，並實測主要流程。

Step 4：清理要連根拔

刪一條 route 從來不是只刪一個 page 檔。連動範圍包括：對應的 component 目錄、只服務這頁的 scss（含散在 responsive 檔裡的 media-query 區塊）、指向這條 route 的按鈕與 router.push、引用這條 route 的 e2e helper 與測試、以及內容已經說謊的註解（例如寫著「成功後導向某頁」但實際流程早就不走那裡）。

實戰：盤點結論被推翻的四個案例

這次最大的收穫不是刪了幾條 route，而是見識到「看起來很確定的盤點結論」可以錯得多徹底。四個真實案例：

案例 1：「站內零引用」是錯的——component 被別頁共用

盤點文件標記某三個 dashboard 頁面「連同 component 目錄整組可刪」。刪除前重新 grep 才發現：其中幾個 component（表格、篩選器）被另一個活著的頁面 import。正確做法是只刪 route 和入口檔，把共用 component 搬到活頁面的目錄下，連同測試一起搬——測試是要搬走，不是刪除。

教訓：盤點是某個時間點的快照，gate 的第一步「刪除前重新 grep」不是儀式，是真的會抓到東西。

案例 2：「有引用」也可能是死的——打不開的 modal

一條付款完成頁（thank-you page），盤點寫「站內零連結」。錯——某個結帳表單裡明明有指向它的 router.push，而且這個表單被兩個保留頁面使用。乍看是活的。

繼續追下去：那個表單被包在 <Modal show={show}> 裡，而 show 的初始值是 false，全 repo 沒有任何一處呼叫 setShow(true)。modal 永遠打不開，那個 router.push 永遠到不了。線上真正的付款流程走的是另一條路，從不經過這頁。

但還沒完——這頁上有轉換追蹤事件，「刪掉會不會掉轉換數據」？逐一查購買追蹤事件的三個呼叫點：

呼叫點 是否在線上路徑
現行付款頁的表單 是——redirect 前就發送
打不開的 modal 裡 否
thank-you 頁本身 否——頁面到不了

去重機制（query param + localStorage guard）的設計是「誰先到誰發、只發一次」，而線上流程由現行付款頁在 redirect 前就發掉了。結論：刪除不會掉轉換追蹤。這種等級的查證，就是 route 清理和 dead code 清理在成本上的差距。

順帶的紀律：查證過程挖出「兩個保留頁面裡整組打不開的付款 modal」這個更大的 dead code，但另開票處理，不混進路由清理——scope 一混，review 和 revert 都會變難。

案例 3：「點下去會 404」實測是跳轉——middleware 在中間接住了

盤點列出五條「指向不存在 route 的連結，點下去會 404」。用 Playwright 在登入／未登入兩種狀態實測後改寫：其中三條被 middleware（proxy 層）攔下來 redirect，使用者看到的是跳轉不是 404；只有兩條是真 404。嚴重度重評，處理的優先序也跟著變。

實測還順帶挖出一段 middleware 裡的死程式碼：某個分支永遠被前面的條件先攔掉，唯一能走到它的角色會被導向一條根本不存在的 route。靜態盤點看不出來，實際走一遍就現形。

教訓：route 的實際行為由整條 request 鏈決定（middleware、redirects、proxy），只看 page 檔和連結會誤判。這也是 Step 2「模擬真實使用者訪問」必須做的原因。

案例 4：站內零連結是刻意的——這頁的讀者不是站內使用者

一條表單頁，站內零連結、零引用，形態上完美符合「可刪」。跟負責人確認後才知道：這是給第三方審核方看的頁面，檔頭註解寫明「intentionally front-end only」。站內零連結是設計，不是遺留。

處理方式不只是「不刪」，而是把它移進 D 區「確認保留」，寫明保留原因——否則下一次盤點它又會被列為可刪候選，同樣的確認成本會一再重付。清理文件的價值有一半在「刪了什麼」，另一半在「查過了、確認要留、為什麼」。

驗證分層

由 AI 到人逐步收斂，一層都不跳：

  1. 多 subagent 交叉檢查：開 2～3 個獨立 subagent 檢查清理內容——立場是「找出刪錯的地方」，不是順著刪除者的思路看一遍。
  2. 既有系統測試：typecheck、lint、test、build 全過。
  3. Smoke test + 人工走訪：實際打開網站逐頁瀏覽，確認核心流程與版面。AI 可以先走一遍並截圖，人再抽查。
  4. Code review：人工檢視所有變更，最後把關。

另外兩個 route 特有的驗證細節：

  • redirect 要保留：站內連結改掉、page 檔刪掉之後，next.config.js 層的 permanent redirect 留著——外部既有連結和 SEO 還靠它。
  • 同名不同物要小心：route 的路徑名稱可能跟後端 API endpoint 撞名——刪 route 時 grep 到的 API 常數完全是另一個東西，不能動。

給清理人員的提醒

  • route ≠ dead code：第三方服務、子網域、return URL、廣告後台、email 樣板、SEO——外部進入點一個都不能漏想。
  • 分區代表確認成本，不代表可刪：站內零引用只證明站內沒人用。每一條都要過 gate。
  • 刪除前重新 grep：盤點是快照，會過期，也會錯。這次 14 條 A 區就修正了 4 條。
  • 有引用不代表活著，零引用不代表死了：案例 2 和案例 4 是同一枚硬幣的兩面——判斷的終點永遠是「實際的執行路徑」和「系統負責人的脈絡」。
  • 實測行為，不要推論行為：middleware 和 redirect 鏈會讓靜態推論失真，登入／未登入各走一遍。
  • 記錄「確認保留」跟記錄刪除一樣重要：不寫下來，下次盤點會重付一次確認成本。
  • 順帶挖出的 dead code 另開票：route 清理的 scope 就是 route，別讓 PR 長成怪物。
  • AI 做搜集與舉證，人做判斷：需要系統熟悉度的決策不要外包給 AI。

成果總結

  • 盤點 70 條 page route，本波刪除 16 條（含連動 component、scss、e2e helper 改寫），其餘逐條標注狀態：待確認、已知要問誰，或確認保留並記錄原因。
  • 這次共變更 88 個檔案，程式碼減少 4,086 行。
  • 將整理過程及方法，整理成一個文件紀錄，作為下一輪清理的起點，以及交接。
  • 順帶修掉真實的行為問題：付款錯誤畫面上一顆把使用者導向白畫面的按鈕。
  • 使用者可見行為與轉換追蹤零中斷。

如果說上一次 dead code 清理的心法是「工具給候選、grep 給證據、不懂脈絡的區域不要碰」，那 route 清理要在前面再加一句：**站內的證據永遠只是半份證據——另一半在系統外面，在熟悉系統的人腦子裡。**這就是為什麼刪一條 route，比刪一萬行 dead code 更難。
