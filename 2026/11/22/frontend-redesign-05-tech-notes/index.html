前端改版實戰（五）：技術補充，rewrite、design token、headless hooks 與量測方法

這是「前端改版實戰」系列的最後一篇。前四篇講 Remote Hunter 改版的過程、取捨、挑戰與 AI 的用法，這篇把過程中值得記下來的四個技術點整理成可以直接參考的做法：用 rewrite 讓新舊頁面共用同一個 URL、用 Tailwind v4 建立 design token、用 headless hooks 讓一套邏輯服務多個畫面，以及怎麼量測一次前端重構的成效。

系列文章：（一）整個過程、（二）Trade-off、（三）挑戰與解法、（四）用 AI 加速、（五）技術補充

本文的程式碼都是為了說明而重寫的最小範例，不是 production code。

一、用 rewrite 讓新舊頁面共用同一個 URL

結構

為什麼不用 page 內 if/else 或兩個 route group，第二篇已經討論過。這裡直接看做法：新版頁面放在真實的 /v2 路徑底下，擁有自己的 root layout；由 middleware 依條件把 /jobs 內部改寫到 /v2/jobs。瀏覽器網址列永遠顯示 /jobs。

決策邏輯

每個請求進來時，middleware 依固定的順序決定要走哪一版。順序很重要：越前面的規則優先權越高。

flowchart TD
    R["請求 /jobs"] --> A{"這個 route 的舊版<br/>已經刪除了？"}
    A -- "是" --> NEW["新版"]
    A -- "否" --> B{"內部人員<br/>強制走舊版？"}
    B -- "是" --> OLD["舊版"]
    B -- "否" --> C{"全站 kill switch<br/>關閉了？"}
    C -- "是" --> OLD
    C -- "否" --> D{"這個 route 在<br/>新版清單裡？"}
    D -- "否" --> OLD
    D -- "是" --> E{"內部人員<br/>強制走新版？"}
    E -- "是" --> NEW
    E -- "否" --> F{"已登入？"}
    F -- "是" --> NEW
    F -- "否" --> G{"這個 route 開放給訪客<br/>且訪客 flag 開啟？"}
    G -- "是" --> NEW
    G -- "否" --> OLD

幾個設計上的考量：

  • 「舊版已刪除」排第一：舊版程式碼已經不存在時，任何 flag 都不能把請求導回舊版，否則會 404。這時的 rollback 只能靠 git revert
  • 「強制舊版」排第二：只要舊版還在，不管其他 flag 怎麼設，內部人員都能立刻看到舊版，重現使用者回報的問題
  • 訪客和會員分開放量：登入後的頁面先上，訪客頁面另外用一個 flag 控制，風險比較好管理

幾個範例省略的細節：

一個請求實際怎麼走

把上面的程式碼串起來，使用者打開一個網址時有三種走法：

sequenceDiagram
    participant B as 瀏覽器
    participant P as proxy
    participant N as Next.js
    alt 打開 /jobs，判定走新版
        B->>P: GET /jobs
        P->>P: shouldUseNewDesign 回傳 true
        P->>N: rewrite 成 /v2/jobs，只在 server 內部
        N-->>B: 新版頁面的 HTML，網址列仍是 /jobs
    else 打開 /jobs，判定走舊版
        B->>P: GET /jobs
        P->>N: 不改路徑，直接交給舊版頁面
        N-->>B: 舊版頁面的 HTML
    else 直接打 /v2/jobs
        B->>P: GET /v2/jobs
        P-->>B: 302 導回 /jobs，加上 noindex
        B->>P: GET /jobs，重新走上面的流程
    end

這裡要分清楚 rewrite 和 redirect：

  • redirect：告訴瀏覽器「去另一個網址」，瀏覽器會再發一次請求，網址列跟著變
  • rewrite：只發生在 server 內部，瀏覽器只發了一次請求，也不知道 /v2 存在

正常的使用者只會走前兩條路。使用者分享出去、搜尋引擎收錄的網址永遠是 /jobs，/v2 只是 server 內部用來分開兩棵頁面樹的路徑。

路徑決定之後，畫面怎麼組出來

proxy 只決定最後的路徑，不碰任何 component。拿到路徑之後，App Router 照檔案系統路由找出要 render 的 layout 和 page，由外往內一層一層套起來。route group 的 (xxx) 不會出現在網址裡，所以兩條路徑會對應到完全不同的兩組檔案：

最後的路徑 root layout route group 的 layout page
/jobs app/(legacy)/layout.tsx，載入 Bootstrap、舊 UI library 無 app/(legacy)/jobs/page.tsx
/v2/jobs app/v2/layout.tsx，只載入新版 Tailwind app/v2/(shared)/layout.tsx app/v2/(shared)/jobs/page.tsx

新舊兩邊的 CSS 能完全分開，靠的就是這一層：兩條路徑從 root layout 開始就是不同的檔案。

(shared) 這一組要用同一個 URL 同時服務訪客和會員，所以它的 layout 會再做一次決定：在 server 端讀登入的 cookie，會員套 (app) 那套有左側側欄的外框，訪客套 (marketing) 那套有 header 和 footer 的外框。因為是在 server 端決定，第一幀就是正確的外框，不會先閃一下訪客版。訪客在頁面裡透過登入 modal 登入時不會整頁重新載入，所以 client 端的外框元件拿到登入狀態後，會自己切換成會員的外框。

陷阱：server 和瀏覽器的 pathname 不一樣

使用者打開 /jobs、被 rewrite 到 /v2/jobs 之後，同一頁會出現兩個不同的 pathname：server 端 render 時，處理的是 rewrite 之後的路由，usePathname() 拿到 /v2/jobs；瀏覽器只知道自己打開的網址，hydration 時拿到 /jobs。這會造成兩個問題：

  • 用 pathname 決定畫面的元件（例如導覽列的 active 狀態）會 hydration mismatch
  • pageview 事件送出 /v2/jobs，analytics 工具裡出現不存在的頁面

解法是新版程式碼一律改用自訂的 hook：

凡是拿 pathname 來決定畫面、或把它送出去的地方，都改用這個 hook。專案裡主要有三類：

  • 側欄、導覽列的 active 狀態：判斷目前在哪一頁，決定哪個項目要亮起來
  • tracking：pageview 和跟路由有關的 event，送出去的路徑要和使用者看到的網址一致
  • 用 pathname 組網址：例如切換 tab 時，把目前的 pathname 加上 ?tab=... 更新網址

以側欄為例：

如果這裡直接用 usePathname()，server render 時拿到 /v2/jobs，沒有任何項目亮起來；瀏覽器 hydration 時拿到 /jobs，Jobs 亮起來。兩邊產生的 HTML 不一樣，React 就會報 hydration mismatch。

這個 hook 對舊版頁面沒有影響：舊版的路徑不會以 /v2 開頭，拿到的值和 usePathname() 完全一樣。所以新舊兩棵樹共用的 tracking 元件也能直接換成它，不用分兩種寫法。規則因此可以訂得很簡單：新版程式碼，以及新舊共用的元件，一律用這個 hook，不必逐一判斷哪個地方會出事。

這條規則也寫進專案的 AI system prompt，避免 agent 開發新頁面時直接用 usePathname()。

二、用 Tailwind v4 建立 design token

關掉預設尺度

Tailwind 預設提供 text-sm、text-lg、rounded-md 這類尺度。問題是設計稿的字級和圓角是用像素定義的（13px、14px、12px 圓角），對應到 Tailwind 的預設尺度時，常常要猜「13px 是 text-sm 還是 text-xs」，最後每個人猜的不一樣，就回到舊系統 113 種字級的狀態。

清掉之後，寫 text-sm 不會產生任何 CSS，只能用 text-13、text-14。這看起來很嚴格，但效果很明顯：新版頁面的唯一字級從 113 種收斂到 28 種。

  • 零 client JavaScript：不需要 ThemeProvider，也不需要 context

三、Headless hooks：一套邏輯、多個畫面

情境

職缺詳情有兩個畫面：

  • 整頁：從外部連結或搜尋引擎進來的職缺詳情頁
  • 側欄 panel：在職缺列表頁點選一個職缺時，右側展開的詳情

兩個畫面的資料、收藏、申請流程、tracking 幾乎完全一樣，差別只在版面和少數行為。

做法：邏輯放在 hooks，元件只負責畫

flowchart TB
    subgraph Hooks["Headless hooks：只有邏輯，沒有 UI"]
        H1["useJobDetail<br/>讀職缺、收藏、tracking"]
        H2["useApplyFlow<br/>申請表單展開、導頁"]
        H3["useDocumentGeneration<br/>AI 履歷與求職信生成"]
    end
    VM["useJobDetailViewModel<br/>把 hooks 組成 view model"]
    H1 --> VM
    H2 --> VM
    H3 --> VM
    VM -- "layout = page" --> P["職缺詳情整頁"]
    VM -- "layout = panel<br/>emitViewEvent = false" --> S["職缺列表的側欄 panel"]

layout 會傳進 useApplyFlow，讓 primaryAction 依畫面有不同的行為，例如在 panel 裡按下去不會離開列表頁。申請表單畫在哪裡、怎麼展開，屬於申請流程本身的細節，這裡省略。

這樣分工之後，要改收藏或申請的邏輯，只要改 hooks，兩個畫面會一起更新；只是調整版面或樣式時，只要改 JobDetailView 或外層容器。如果版面的改動需要新的資料或動作，例如多顯示一個欄位、多一個按鈕，還是要先在 view model 補上，view 才拿得到。

差異靠參數，不靠複製

最典型的差異是瀏覽事件。整頁打開時要送一次「職缺被瀏覽」的事件；但在列表頁的側欄 panel 裡，這個事件應該由列表那一側送出，因為列表才知道這個職缺在搜尋結果裡排第幾名。如果兩邊都送，數據就會重複。

所以 panel 傳 emitViewEvent: false，由列表送出帶有搜尋排名的事件：

同一套邏輯，用參數處理差異，而不是複製一份 hooks 再改。

舊 hook 綁死舊 UI 時：寫一個新版對應物

有些舊版 hook 綁死了舊版 UI（例如直接呼叫舊的 toast 或 modal）。這時不改舊版 hook，而是寫一個同樣介面的新版 hook：邏輯照搬，只換掉 toast、modal 這些「出口」；真正共用的部分（例如 API 呼叫）則抽到兩邊都能 import 的共用層。

四、怎麼量測一次前端重構的成效

原則

原則 為什麼
只比相對差，不看絕對值 本地環境的絕對值不能代表 production，但同一台機器上新舊版本的差異是可信的
用同一個 build 做 A/B 還保留舊版的頁面，用 query string 切換新舊版，排除 build 差異
舊版已刪除的頁面，用改版前的 build 對照 用 git worktree 另外 build 一份改版起點的程式碼
每個 URL 跑多次取中位數 桌機跑 5 次、模擬手機跑 3 次，避免單次的雜訊
量的單位是「頁面」和「新版程式碼樹」，不是整個 repo 舊版頁面還在 repo 裡時，整個 repo 的總數會稀釋改善的幅度
改版期間的其他功能開發要分開歸因 起點到終點之間不只有改版，整樹的數字要按目錄拆開

量哪些指標、用什麼工具

面向 指標 工具
靜態程式碼 !important 數量、自訂 CSS 行數、新版程式碼是否 import 舊 UI 框架 shell script（grep）
每頁下載量 實際載入的 CSS / JS bytes（gzip）、請求數 啟動 production server，解析頁面引用的 asset
CSS 結構 rule 數、selector 複雜度、specificity、唯一字級與顏色數 @projectwallace/css-analyzer
載入速度 FCP、LCP、load、TBT、CLS Playwright + Chrome DevTools Protocol
執行期成本 JS heap、DOM 節點數、style recalc 時間 Chrome Performance.getMetrics
綜合分數 Performance、Accessibility Lighthouse（mobile preset）

手機情境用 Chrome DevTools Protocol 模擬 slow 4G（150 ms RTT、1.6 Mbps）加上 4 倍 CPU 節流。

追根因：把 long task 拆開

瀏覽器的 longtask（PerformanceObserver）只告訴你「有一個 50ms 以上的任務」，不告訴你任務裡在跑什麼。要知道是哪段 JavaScript 或哪次 layout 在吃時間，可以在 Playwright 裡用 CDP 的 Tracing：

收集到事件後：

  • 取 name === 'RunTask' 且 dur > 50000（微秒）的事件當作 long task
  • 把時間區間落在 long task 裡的 FunctionCall、EvaluateScript、Layout 事件，依來源檔案加總，就知道是哪個 chunk 或哪次 layout 在吃時間
  • Layout 事件如果落在某個 FunctionCall 裡面，就是 forced synchronous layout，stackTrace 會告訴你是誰觸發的

想驗證「是不是動畫造成的」，可以用 Playwright 的 reducedMotion: 'reduce' 做對照，不需要改程式碼。

常見的陷阱

  • standalone 模式不會 serve 靜態資源：Next.js 的 standalone server.js 不會 serve .next/static，CSS 和 JS 全部 404，但頁面本身回 200。量下載量之前，先確認任一個 asset 回 200，或改用 next start
  • 切換版本的 cookie 會殘留：用 query string 切換新舊版本時，如果會寫 cookie，同一個瀏覽器 context 連續量測就要記得清 cookie
  • grep ! 會誤判：Tailwind v4 的 important modifier 是 ! 開頭（例如 !p-4），直接 grep ! 會把 JavaScript 的 !isOpen 也算進去，要限定 utility 名稱
  • LCP 元素可能不同、prefetch 的資源不在 bundle 裡：案例見第三篇

寫成可重現的文件

最後，把量測方法寫成一份文件：起點和終點的 commit、每個指標的指令、已知的陷阱。這樣之後把剩下的舊頁面全部移除時，可以用同一套方法再量一次，得到可以直接比較的第三個時間點。

系列結語

這個系列從過程、取捨、挑戰、AI 協作一路寫到技術細節。如果只能留下一句話，我會選這句：大型前端重構的關鍵，不是一次寫出完美的新版，而是讓新舊版本能安全地並存、可以量測、可以隨時退回。有了這三件事，剩下的就是一頁一頁、按部就班地做完。
