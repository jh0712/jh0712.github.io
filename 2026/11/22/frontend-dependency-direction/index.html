前端元件的依賴方向：改一個檔案，為什麼會影響到不相干的地方

前端改版時，我花了不少時間在一個問題上：改一個元件，到底會影響幾頁？這篇整理我對「依賴方向」的理解：箭頭怎麼讀、為什麼只能往下、違反方向有哪兩種情況，以及元件的依賴要怎麼設計，才能讓改的人事先知道影響範圍。

這篇是從 前端改版實戰（二）：Trade-off 的「共用元件什麼時候抽」延伸出來的。

先學會讀箭頭：A → B 是「A 需要知道 B」

依賴圖上的一條箭頭 A → B，代表 A 的程式碼裡 import 了 B。我習慣把它讀成：A 需要知道 B。

A 需要知道 B 放在哪裡、叫什麼名字、export 出來的東西長什麼樣子。所以：

  • B 改了 export 的格式，A 可能要跟著改
  • B 搬家或改名，A 會直接編譯失敗
  • 想刪掉 B，得先處理 A

反過來，B 完全不需要知道 A 的存在，A 改什麼都不會影響到 B。

這個不對稱就是依賴方向的意義：箭頭的起點承擔「對方改動」的風險；終點則背負「被依賴」的責任，指向它的箭頭越多，它越不該隨便改。

分層：跨層的箭頭只能往下

把前端的程式碼分成幾層：

flowchart TD
    P["Page<br/>頁面本身與只有它用到的元件"] --> D["Domain<br/>有業務語意的共用元件<br/>職缺卡片、上傳履歷 modal"]
    P --> DS
    D --> DS["Design system<br/>沒有業務語意的元件<br/>Button、Modal、Tabs"]
    DS --> T["Design tokens<br/>顏色、字級、圓角、尺寸、斷點"]

第二篇的分層圖還有一層 Shell（root layout、側欄、header），它和 Domain 一樣夾在頁面和 Design system 之間。這篇的例子用不到，所以省略。以下把 Design tokens 簡稱為 Tokens。

規則是：

  • 跨層只能往下：上層可以 import 下層，下層永遠不 import 上層
  • 同一層的共用元件可以互相 import，但不能形成循環：例如一個 Domain 元件用到另一個 Domain 元件
  • 不同頁面的私有檔案不互相 import：另一個頁面也需要，就先搬到共用層

為什麼是往下？因為越往下，被越多地方依賴：

層 被誰依賴 預期的修改頻率 該有的保護
Page 沒有人 最高，需求都落在這裡 這一頁的測試
Domain 好幾個頁面 中等 單元測試、tracking event 檢查
Design system 所有頁面 低 每個元件都有 Storybook story
Tokens 所有元件 最低 token 一致性檢查

Robert C. Martin 把這叫做 Stable Dependencies Principle：依賴應該指向比自己更穩定的東西。

這裡的「穩定」不是指改得少。Martin 的定義是：一個模組被很多模組依賴、自己又很少依賴別人，改它的阻力就很大，所以是穩定的。底層正是這樣：被所有頁面依賴，自己只依賴更底層的東西。這樣的模組如果反過來依賴一個常改的頁面，頁面的每次修改都會透過它傳到所有依賴它的地方。Martin 原本講的是套件之間的依賴，套用到資料夾分層一樣成立。

下面的範例用這樣的目錄：app/ 放路由，features/<頁面>/ 放頁面私有的元件和設定，components/ 放 Domain，design-system/ 放 Design system，design-system/tokens/ 放 Tokens。

例子一：Tokens 引用了頁面的設定

最直接的反例是：你要改職缺詳情頁的版型，卻得連帶修改 Tokens，因為 Tokens 引用了這個頁面的設定。

    P["用到這些元件的頁面"] --> C["用到 size.ts 的<br/>共用元件"]
    C --> T["Tokens<br/>size.ts"]
    T -.->|"往上 import"| L["職缺詳情頁<br/>sidebar-config.ts"]

把圖從左讀到右，問題就很清楚了：用到 size.ts 的共用元件，以及用到這些元件的頁面，全都間接依賴了一個頁面的設定檔。Tokens 通常被大部分元件用到，所以這個範圍幾乎就是整個網站。

實際會遇到的後果：

  • 改名就壞：只是把 features/job-detail/ 改名，連共用的 Tokens 都會編譯失敗
  • 改版面會波及其他頁面：職缺詳情頁想把 width 改成別的格式，例如拆成手機和桌機兩個值，size.ts 也得跟著改，用到它的元件都可能受影響
  • 刪不掉：之後職缺詳情頁改版、想整個資料夾重寫，得先回頭處理 Tokens
  • 隨時可能出現循環依賴：哪天 sidebar-config.ts 想用一個 token，例如 size.panelMd，就變成 size.ts → sidebar-config.ts → size.ts。依載入順序，原生 ES module 會在初始化時丟出 ReferenceError: Cannot access 'size' before initialization；轉成 CommonJS 的環境（例如部分測試設定）則是拿到 undefined。而且錯誤出現的位置，通常不是造成循環的那一行

正常的方向反過來寫，讓頁面決定側欄要選哪個尺寸：

flowchart TD
    L["職缺詳情頁<br/>sidebar-config.ts"] --> T["Tokens<br/>size.ts"]
    C["Button、Modal 等<br/>共用元件"] --> T

這樣職缺詳情頁想換寬一點的側欄，只要改成 size.panelLg，Tokens 完全不用動。如果 320px 只是這一頁的特殊需求，沒有其他地方會用到，也可以直接把數字留在頁面的 sidebar-config.ts，不必硬塞進 Tokens。

命名不等於依賴

有個容易混淆的細節：如果 Token 取名叫 jobDetailSidebarWidth，它算不算依賴了職缺詳情頁？

不算。這只代表命名綁定了頁面情境。判斷程式碼的依賴方向，要看兩件事：

  • 值由誰提供：320px 是寫在 Tokens 裡，還是從頁面拿來的
  • 誰引用誰：是頁面 import Tokens，還是 Tokens import 頁面

這段的依賴方向是對的，頁面改名或刪除都不會讓它編譯失敗。

不過這樣命名還是有代價，只是代價在設計上，不在依賴上：名字綁了頁面，大家就會把它當成那一頁的東西。職缺詳情頁要改寬度時，會直接改這個 token，卻沒發現另一個頁面的側欄也剛好用了它。用 panelMd 這種描述尺寸本身的名字，比較不會被當成某一頁私有的。

例子二：程式碼沒問題，只是放錯了位置

例子一是 Tokens 自己 import 了不該 import 的東西。還有另一種違反方向，程式碼本身完全沒問題，問題出在檔案放的位置。

前端改版時，我抽查到一個「履歷拖放上傳區」元件，放在設定頁的資料夾裡。看位置，它是設定頁私有的；但實際上還有三個地方在用它：

flowchart LR
    P1["設定頁<br/>頁面層"] -->|"同一頁，正常"| X["履歷拖放上傳區<br/>放在設定頁的資料夾裡<br/>看起來是設定頁私有的"]
    P4["Dashboard<br/>頁面層"] -.->|"跨頁 import"| X
    D1["上傳履歷 modal<br/>Domain 層<br/>職缺列表、職缺詳情頁在用"] -.->|"往上 import"| X
    D3["自動申請的上傳履歷步驟<br/>Domain 層"] -.->|"往上 import"| X

這個元件本身只 import 了 React、icon、檔案格式與大小上限的常數，以及 design system 的 Spinner，沒有 import 任何頁面的檔案。它的職責也切得很乾淨：只負責選檔，選好的檔案交給呼叫端，要不要上傳、上傳完做什麼，都由呼叫端決定。它自己沒有做錯任何事。

問題是位置說的話和實際用途不一致。用三個假設的修改來比較：

修改 檔案放在 從位置判斷會影響 實際會影響
按鈕圓角從 8px 改成 12px Design system 所有頁面 所有頁面，符合預期
職缺卡片的薪資移到標題下方 Domain 有職缺卡片的頁面 同左，符合預期
設定頁希望上傳完成後直接跳到履歷列表，改的人把跳頁寫進這個元件 設定頁的資料夾 只有設定頁 設定頁、Dashboard、職缺列表與職缺詳情頁的上傳 modal、自動申請設定流程

前兩個修改也會讓好幾頁一起變，但改的人事先就知道。第三個需求本身沒錯，在設定頁管理履歷，上傳完跳到列表很自然；但改的人看位置，以為這個元件是設定頁私有的，就把上傳和跳頁直接寫進元件裡，也只測了設定頁。結果使用者在職缺頁面打開上傳 modal 補一份履歷，上傳完就被帶離那個職缺；在自動申請設定流程上傳，也會被中途帶走。這個修改是假設的，但只要位置不改，遲早會有人照位置做判斷。

修法是把檔案搬到 Domain 層，並更新所有 import 路徑：

flowchart TD
    P1["設定頁<br/>頁面層"] --> X["履歷拖放上傳區<br/>Domain 層"]
    P4["Dashboard<br/>頁面層"] --> X
    P2["職缺列表、職缺詳情頁<br/>頁面層"] --> D1["上傳履歷 modal<br/>Domain 層"]
    D1 --> X
    D3["自動申請的上傳履歷步驟<br/>Domain 層"] --> X
    X --> B["Spinner 等<br/>Design system"]

搬完之後，誰 import 誰完全沒變，改它一樣會影響同樣的地方。變的是分層的宣告：它現在放在 Domain 層，改的人一看位置就知道它是共用的。

這也說明了依賴方向到底是什麼：它是把「實際的 import 關係」拿去對照「宣告的分層」得到的結果。同一條 import，兩端放在哪一層，決定了它是往下、同層，還是往上。在大部分前端專案裡，分層是用資料夾宣告的，所以人看路徑猜影響範圍，lint 規則也是比對路徑。資料夾放錯，人會猜錯；工具也只擋得住寫成規則的那幾條，例如 Domain 往頁面的資料夾拿元件，頁面之間互相拿就擋不住。

違反方向的兩種情況

把兩個例子放在一起：

依賴錯對象 放錯位置
狀況 元件本身 import 了比它高層的東西 元件本身沒問題，只是放在不代表它真實用途的地方
例子 Tokens import 了職缺詳情頁的 sidebar-config.ts 好幾個地方在用的拖放上傳區，放在設定頁的資料夾
怎麼看出來 看這個檔案自己 import 了什麼 看有誰 import 這個檔案
修法 改程式碼：把值或決定交給上層，例如讓頁面選 token、用 props 或 callback 傳進來 確認它真的是共用的之後，搬到共用層並更新所有 import 路徑
只搬資料夾有用嗎 沒用。只換 size.ts 的路徑、不改它 import 的東西，它還是依賴頁面的設定 有用

第一種比較危險，因為它真的把穩定的東西綁在常改的東西上。第二種的影響範圍本來就存在，只是被藏起來了。

怎麼設計比較好

1. 檔案位置就是宣告

只有一頁用的元件放在頁面旁邊，用相對路徑 import。第二個頁面需要它時，在同一個 PR 裡把它搬到 Domain 或 Design system，不要從另一個頁面的資料夾裡拿。這樣「放在頁面旁邊」才真的代表「只有這一頁在用」。

一個簡單的訊號：頁面私有的相對路徑應該只有 ./。出現 ../另一個頁面/，就是在跨頁拿東西；例子二的 Dashboard，就是用 ../ 跨到設定頁的資料夾拿元件。

2. 共用的東西提供選項，使用者做決定

例子一的修法是 Tokens 提供 panelMd、panelLg，由頁面選要用哪一個。元件也是一樣，例子二的拖放上傳區本身就是很好的示範：它只負責「選檔」，把選好的檔案交給呼叫端。要不要馬上上傳、上傳完要跳頁、要選定給某個職缺、還是進到下一步，都是使用它的地方才知道的事。

useResumeUpload 代表負責上傳的 hook，回傳上傳後的履歷。例子二那個「上傳完跳到列表」的需求，正確的做法就是這樣：讓設定頁在自己的 callback 裡處理，共用元件完全不用改。如果把上傳和 router.push('/settings/resumes') 直接寫進共用元件，就會從「放錯位置」變成「依賴錯對象」：共用元件開始需要知道設定頁的路由。

Design system 要再嚴格一點：props 只描述外觀和行為，例如 variant、size、disabled，不收 job、resume 這種業務物件。

3. 共用元件裡出現「是哪一頁」的判斷，就是抽錯了

典型的徵兆是 if (page === 'settings')，或越來越多只有一個地方會傳的 boolean props，例如 isSettingsPage、hideTitleOnDashboard。這代表元件被迫知道上層的事，等於是一條不會出現在 import 裡的往上依賴：lint 和依賴圖都看不到它，只能靠 review 發現。

修法是把差異往上推：用 callback、用 children 組合，或乾脆拆回各自的頁面。Sandi Metz 在〈The Wrong Abstraction〉裡有一句話很適合這個情況：重複的程式碼，比錯誤的抽象便宜得多。

這和「第二個使用者出現就抽」並不衝突。兩邊做的是同一件事、業務意義相同，才抽成共用；只是長得像、業務意義不同，就留著重複，讓它們各自演進。

4. 邏輯和畫面分開共用

兩個頁面需要同一套資料和流程，但畫面不一樣時，把邏輯放進 headless hook（只有狀態和行為、不回傳任何畫面的 hook，第五篇有更多說明），畫面各自組合。共用邏輯不代表要共用畫面，這樣一個頁面改版面時，就不會動到另一個頁面。

5. 不要有循環

A → B → A 時，兩個檔案實際上綁成一個單位：很難單獨測試、單獨修改或刪除，初始化順序也變得脆弱。例子一就是循環的溫床：Tokens 一旦往上 import 了頁面的設定，那份設定（或它 import 的檔案）只要用到同一個 token 檔，就形成循環。Robert C. Martin 把這叫做 Acyclic Dependencies Principle；和 Stable Dependencies Principle 一樣，他原本講的是套件之間，套用到檔案之間也成立。

6. 把規則寫成工具，不只靠 review

文件和 code review 會忘，lint 每次都會檢查。改版期間我們沒有這組設定，規則是靠 review 守的，例子二就是這樣漏掉的（見第二篇第 8 題的代價）。下面是回頭看會補上的設定，用 eslint-plugin-import 禁止特定目錄 import 另一個目錄，並抓出循環：

第一個 zone 擋下 Tokens 往上 import Design system 的元件；第二個擋下例子一；第三個擋下例子二裡兩個 domain 元件的 import；no-cycle 抓到 size.ts 和 sidebar-config.ts 互相 import。我用 ESLint 9 和 eslint-plugin-import 2.32 實跑過這組設定，改成正確的寫法之後就是 0 個錯誤。

要注意的是，settings 裡的兩項少了任何一項都不會報錯，只會靜默失效：

  • 沒有 resolver：@/ 開頭的 import 解析不到，規則直接略過，lint 照樣通過
  • 沒有 parsers：no-cycle 對 .ts 檔完全不報。@typescript-eslint/parser 也要裝在專案自己的 dependencies 裡，讓 plugin 找得到

Next.js 專案如果已經用了 eslint-config-next，它已經註冊好 import plugin 和這兩項 settings，只要加上 rules 那段就好；其他專案要自己補齊。最保險的驗證方式是故意寫一條違規的 import，確認 lint 真的會失敗。

lint 擋不住的有兩種：頁面之間互相 import（可以用 except 逐頁列舉，但頁面一多就難維護，改用 dependency-cruiser 這類工具比較好寫），以及第 3 點那種不會出現在 import 裡的往上依賴。

另外兩件小事也有幫助：

  • 不寫 barrel index.ts：barrel 是只負責 re-export 同目錄元件的 index.ts，讓大家可以寫 from '@/design-system'。不寫它，import 路徑就會寫出元件的檔名，grep 能直接找到每個使用的地方（見第二篇第 9 題）
  • 改共用元件前，先列出所有使用者：用 grep，或 madge、dependency-cruiser 這類能從依賴圖反查「誰依賴這個檔案」的工具，列出會跟著變的頁面

什麼時候該抽成共用

太早抽，容易抽錯，元件裡最後塞滿只為某一頁存在的 props；太晚抽，同一段 JSX 會被複製到好幾個地方，各自長歪。改版正式搬遷頁面時，我用的折衷是第二個使用者出現時才抽（設計稿剛切成元件時，則是先盤點再抽，見第二篇第 8 題）：

  • 第一次寫：放在頁面旁邊，不急著共用
  • 第二個頁面需要：在同一個 PR 裡搬到共用層，兩個使用處一起改成 import 新位置
  • 如果兩邊只是長得像，業務意義不同，就各留各的

有些團隊用 rule of three（Don Roberts 提出、經 Martin Fowler 的《Refactoring》推廣），等第三個使用者出現才抽，換取對抽象更有把握。兩種都可以，重點是不要讓第二個使用者直接從第一個頁面的資料夾裡拿。

新增或修改元件前的檢查

  • 現在有幾個地方用它？只有一個，放在頁面旁邊；兩個以上，放到共用層
  • 它有業務語意嗎？有，放 Domain；沒有，放 Design system 並補一個 story
  • 我要 import 的檔案在哪一層？在比我高的層，或在另一個頁面的資料夾裡，先把它搬到共用層，或改成由上層傳進來
  • 這次修改是所有使用者都要，還是只有這一頁要？只有這一頁要，用 props、callback 或選另一個 token，不改共用的預設值
  • 改共用的東西之前，知道所有使用的地方嗎？用 grep 或依賴圖工具，列出會跟著變的頁面，逐一檢查

結語

改一個共用元件會影響好幾頁，這本身不是問題，那正是抽出共用元件的目的。真正的問題是改的人事先不知道。

依賴方向要做的，就是讓「檔案放在哪裡」可以被信任：放在頁面旁邊的只影響這一頁，放在 Domain 的影響用到它的頁面，放在 Design system 和 Tokens 的影響全部。只要箭頭都往下，看一眼路徑就能知道影響範圍大概落在哪裡，精確的範圍再交給依賴圖去算；工具再把箭頭的方向守住，這個判斷就不會在某一天悄悄失準。
