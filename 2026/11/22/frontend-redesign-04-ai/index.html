前端改版實戰（四）：我怎麼用 AI 加速一個 19 頁的前端改版

這是「前端改版實戰」系列的第四篇。Remote Hunter 這次 19 個頁面的改版，從切元件、規劃、開發、驗證到量測成效，每個階段都有 AI 參與（主要使用 Claude Code，model 是 Opus 5）。這篇整理 AI 在每個階段做了什麼、哪裡好用、哪裡會出錯，以及我怎麼調整和它合作的方式。

系列文章：（一）整個過程、（二）Trade-off、（三）挑戰與解法、（四）用 AI 加速、（五）技術補充

總覽：AI 在每個階段的角色

階段 AI 做什麼 我做什麼
前置清理 找出 dead code、沒有入口的 route，產出風險報告 決定禁區、review 報告
切元件 把 HTML 設計稿切成 19 頁、約 70 個 React 元件、約 190 個 story 定架構與規則、一頁一頁對齊設計稿，跟設計師對稿
規劃 分析哪些元件可以共用、哪些不行，寫計畫文件 判斷合不合理、決定先後順序
開發 4 到 5 個 agent 平行開發不同頁面 分派任務、review、處理跨頁面的決策
驗證 用瀏覽器自動操作頁面、截圖、比對 看截圖、做最後的驗收
量測 設計量測方法、跑量測、寫評估報告、追根因 判斷結論是否成立、決定要修什麼

整體的分工原則跟我在 從 AI 寫 Code 到管理 AI 裡寫的一樣：AI 負責產出和舉證，人負責判斷和決策。

切元件：兩天把 19 頁設計稿變成 React 元件，但不能全信

給 AI 的 prompt

設計師交付的 prototype 是一份 HTML 設計稿。我要把它切成 React 元件，同時定下之後新版前端的架構。給 AI 的第一個 prompt 大概是這樣：

最後一句「有什麼問題嗎？」很重要：它讓 AI 先提出疑問、確認需求，而不是直接開始寫。

AI 回答完問題後，產出了一份 plan.md。我確認計畫沒問題，接著只給了一句：

大約兩個工作天，19 個頁面、約 70 個共用元件、約 190 個 Storybook story 就完成了。AI 還額外做了一個索引頁，把所有頁面列在一起，方便之後逐頁對照驗收。

遇到的問題：幻覺與偷懶

產出很快，但不能直接用：

  • 幻覺：有些頁面的內容是 AI 自己編的，設計稿裡根本沒有
  • 頁面越多，品質越差：實際測試下來，一次讓 AI 處理 2 到 3 個頁面，完成度最高；超過 5 個頁面，它就開始偷懶，也更容易出現幻覺

我的理解是：頁面一多，context 被塞滿，AI 對每一頁的注意力就被稀釋了。後來我就把任務切小，一次只給 2 到 3 頁。

人工對稿

AI 產出之後，我一頁一頁對齊設計稿、修正錯誤，再請設計師核對。設計師在 web 和 mobile 兩種尺寸下又找出 44 處不一致，全部修正後才定案。

這一步沒辦法省。AI 能很快產出「看起來對」的東西，但「是不是設計師要的」只有人能判斷。

如果再來一次

回頭看，第一版的產出比較著重在我有提出的部分。我給 AI 的 prompt 只講了專案架構的需求和要遵守的規定，例如 Tailwind、共用元件、Storybook、Next.js 16，並沒有要求它先理解設計稿本身。所以它把力氣花在架構上，設計稿裡的細節則是靠後來的人工對稿才補齊。

如果再來一次，我會在切元件之前多加一層：先開幾個 AI agent 分頭讀設計稿，把原本畫面的細節整理成一份 checkpoint 清單，例如：

  • 動畫：哪些元素有過場、hover、展開收合的效果
  • 頁面樣式：間距、字級、顏色，以及不同寬度下的排版
  • 流程步驟：一個流程有幾步、每一步顯示什麼
  • 按鈕的連接方向：每個按鈕和連結點下去會到哪裡

這份清單就是 before 的基準。切完元件之後，再另外啟動一個負責驗收的 AI，逐條對照 checkpoint 檢查新做的畫面，有問題就立刻修正，而不是等到最後才由我和設計師一頁一頁對。這和開發階段讓 agent 自己截圖驗證是同一個想法，只是把驗收的基準往前移到設計稿。

這樣做有兩個好處：

  • 產出和驗收用同一份標準：開發的 agent 知道要對齊什麼，驗收的 agent 知道要檢查什麼，比較不會出現「AI 只做了我有講的部分」
  • 問題在當下就被抓到：一次做對的比例和產出品質都會提高，人工對稿可以把時間留給真正需要判斷的地方

規劃：AI 當分析師，我當審核者

19 個頁面要搬到正式專案，順序和共用元件的切法會影響後面所有的工作。我讓 AI 先做分析：

  • 哪些元件在多個頁面出現、可以共用
  • 哪些元件看起來相似，但業務邏輯不同，不應該合併
  • 每個頁面依賴哪些 API、有哪些 tracking event

然後由我判斷：

  • 哪些分析合理、哪些不合理
  • 哪些頁面先做、哪些後做（第一篇提到的「從低風險到高風險」）
  • 哪些地方需要跟需求方或其他工程師溝通

計畫寫成文件放在 repo 裡，每完成一個階段就讓 AI 根據實際遇到的問題更新計畫。所以這次的計畫不是一開始就定案的，而是邊開發邊修正的。

開發：4 到 5 個 agent 平行工作

怎麼分工

我用 cmux（一個類似 tmux 的終端管理工具）管理多個終端 session，搭配 git worktree，讓每個 agent 在獨立的工作目錄裡開發：

  • 一個 session 當總管：負責分派任務給底下的 session、追蹤每個 session 的進度
  • 每個任務一個 worktree：每個 worktree 有自己的分支、自己的 dev server，程式碼不會互相干擾，每個任務都可以獨立交付、獨立驗收
  • 同時 4 到 5 個：每個 agent 一次負責 2 到 3 個頁面

一個任務從分派到交付，大致是這樣：

sequenceDiagram
    participant Me as 我
    participant M as 總管 session
    participant A as agent
    participant B as 瀏覽器
    Me->>M: 任務與驗收條件
    M->>A: 分派 2 到 3 頁（各自的 worktree 與 dev server）
    A->>A: 開發
    A->>B: 操作頁面、在不同寬度下截圖
    B-->>A: 截圖與操作結果
    A->>M: diff、驗證步驟、截圖
    M->>Me: 彙整
    Me->>A: review 通過或退回

cmux 的用法，我在 讓 Claude Code 把工作丟給 Codex 裡有提過。

自動驗證

每個 agent 做完之後，不是直接交給我 review，而是先自己驗證一輪：

  • 用 agent-browser（給 AI agent 用的瀏覽器自動化 CLI）或 Playwright 打開自己的 dev server
  • 依照任務的驗收條件操作頁面（點擊、填表、切換 tab）
  • 在不同的螢幕寬度下截圖
  • 把截圖和操作結果附在交付內容裡

我拿到的是「改了什麼 + 怎麼驗證的 + 截圖」，而不是只有一份 diff。這大幅節省了我的驗證時間：大部分的問題在截圖裡就看得出來，不用每個都自己開瀏覽器確認。

讓 AI 守規則：文件、prompt 與檢查腳本

agent 一多，最怕的是每個 agent 寫出來的風格不一樣。我用三層機制讓 AI 遵守同一套規則：

  1. DESIGN.md：記錄 design token、元件目錄、import 規則、依賴方向。這份文件在切元件階段由 AI 產出，之後隨著專案演進持續更新，並在新版確定後改成正式的 design system 文件
  2. 專案的 system prompt：告訴 AI 新版程式碼要放在哪裡、不可以 import 什麼，以及第二篇那三條抽元件的規則（第二個頁面需要時才抽、有業務語意的放 domain 目錄、沒有的放 design system 並補 story）。過渡期還會加上暫時性的規則，例如第三篇提到的「這段期間要同時維護新舊兩頁」
  3. 檢查腳本：有些規則光靠文件守不住，就寫成腳本，例如：
    • design token 的定義和程式碼裡的使用是否一致
    • 新舊兩個 root layout 是否掛了同一組 analytics 元件
    • 新版程式碼裡有沒有寫死的主色色碼

回頭看，第三層最可靠。文件和 prompt 是「建議」，腳本是「規則」；AI 偶爾會忽略建議，但不會繞過一個會 fail 的檢查。不過目前這些腳本還要手動跑，下一步是接進 CI，變成真正擋得住的關卡。

量測：讓 AI 設計並執行成效評估

改版做完之後，我想回答一個問題：新版到底有沒有比舊版好？這部分幾乎都是讓 AI 協助完成的。

flowchart LR
    A["設計量測方法<br/>定義起點與終點<br/>決定量哪些指標"] --> B["準備兩份 build<br/>用 worktree 分別 build<br/>改版前與改版後"]
    B --> C["執行量測<br/>靜態程式碼指標、每頁下載量<br/>CSS 結構、Lighthouse<br/>真實瀏覽器量測"]
    C --> D["寫評估報告<br/>每個數字附上量測條件"]
    D --> E["找出例外<br/>追根因"]
    E --> F["修正後補測"]
    F --> D

每個數字怎麼量、用什麼指令、有哪些陷阱，都寫進一份方法文件，之後任何人都能用同一套方法再量一次（細節見第五篇）。

AI 幫我抓到的東西

最有價值的不是那些漂亮的百分比，而是 AI 在量測過程中發現的「例外」：

  • 第三篇的兩個效能陷阱（rollback 路徑帶回舊 CSS、<Link> prefetch 舊頁面），都是先出現在報告的「例外」欄，再讓 AI 追根因找到的
  • 有一頁的 LCP 看起來變差，AI 用 PerformanceObserver 抓出兩個版本的 LCP 元素，發現它們量的根本是不同的東西
  • 有一頁的 TBT（Total Blocking Time）比舊版多，直覺上會以為是新的動畫造成的。AI 用 Chrome DevTools Protocol 錄 trace、把每個 long task 拆開歸因，發現真正的原因是 hydration 時第一次 layout 的成本，跟動畫無關

數字看起來很合理的陷阱

量測過程中有幾個很容易踩、而且數字看起來很合理的陷阱，都記在方法文件裡：

  • 用 standalone 模式啟動 Next.js 時，靜態資源會全部 404，但頁面本身還是回 200。如果沒先檢查，量到的「下載量」會小得很漂亮，但完全是錯的
  • 用 grep ! 計算 Tailwind 的 important modifier（例如 !p-4）時，會把 JavaScript 的 !isOpen、!hasError 也算進去
  • 用同一個瀏覽器 context 連續量新舊版本時，切換版本的 cookie 會殘留，導致量到錯的版本

這些陷阱的共通點是：數字看起來很合理。如果我只看報告的結論，很可能就直接相信了。所以我會要求每個數字都附上量測條件，並且抽查幾個「好得不太合理」的數字。

心得

當初沒算進去的收益

改版完成後，有幾個收益是一開始沒預期到的：

  • 設計師開始整理一套 design system：之後的設計稿可以直接對應到現有的元件，設計和開發的語言終於一致
  • component library 可以重用：新功能不用再從零刻畫面
  • AI 返工變少：component library 和設計風格定型後，AI 只要組合現有的元件，產出的畫面就很接近設計師要的樣子，返工的次數和 token 消耗都比改版前少

人的價值在判斷

AI 能在兩天內把 19 頁設計稿切成 React 元件，但它不知道哪些內容是自己編的；它能跑出完整的量測報告，但不知道哪個數字「好得不太合理」。這次改版裡，我花最多時間的地方不是寫程式，而是判斷：判斷 AI 的分析是否合理、判斷哪個頁面該先做、判斷哪個數字可以相信。

下一步

接下來我會再調整專案的 system prompt：告訴 AI 哪些畫面是既有、要保留的，哪些需求會動到舊設計，讓之後的新頁面一律走新風格，而不是在舊頁面上修補。改版做完不是終點，讓 AI 之後也能持續產出符合新設計的東西，才是這次改版真正的長期價值。
