前端改版實戰（二）：Trade-off，這次改版我放棄了什麼

這是「前端改版實戰」系列的第二篇。上一篇講了 Remote Hunter 19 個頁面從舊設計搬到新 design system 的完整過程，這篇回頭看過程中做的九個取捨：每一個都有放棄的東西，有些到現在還在付代價。每個取捨都用「情境、選項、選擇、代價、回頭看」整理；第 7 和第 9 個沒有明確的替代方案，就只寫選擇和代價。

系列文章：（一）整個過程、（二）Trade-off、（三）挑戰與解法、（四）用 AI 加速、（五）技術補充

九個取捨分成三類：架構、流程、程式碼組織。

架構上的取捨

1. 整頁重構，還是元件逐步替換

情境：舊頁面混用 Bootstrap、Tailwind 和兩套 UI library，全域樣式會互相污染。

選項：

  • A. 在舊頁面裡一個元件一個元件換成新設計
  • B. 以頁面為單位，整頁重寫成新版

選擇：B。

A 看起來風險比較小，每次只動一點點。但實際試過之後，新元件放進舊頁面就會被 Bootstrap 的全域 reset 和 SCSS 的全域 selector 影響，要長成設計稿的樣子，就得再寫一層 !important 蓋回去。這等於用新的技術債蓋舊的技術債。

代價：每一頁都是「全有或全無」。一頁沒做完就不能上線，單一 PR 也會比較大。核心頁面的重構期間，其他人在舊頁面上的修改還得再搬一次。

回頭看：在全域樣式污染這麼嚴重的專案裡，逐步替換只是看起來比較安全。

2. 新舊頁面怎麼並存在同一個 URL 下

情境：既然要整頁重寫，新舊版本就得共存一段時間。使用者看到的 URL 不能變（SEO、廣告連結、外部分享都依賴它），但新版和舊版要能各自上線、各自 rollback。

選項：

  • A. 在同一個 page.tsx 裡依 feature flag 做 if/else，分別 render 新舊元件
  • B. 用 Next.js App Router 的 route group 分出兩棵樹
  • C. 開一個真實的 /v2 路徑放新版頁面，由 middleware 依條件把 /jobs 內部改寫（rewrite）到 /v2/jobs

選擇：C。

A 的問題是 CSS：同一個 page 底下的 layout 會把 Bootstrap 和舊的 SCSS 一起載入，新版頁面還是會被污染。B 的問題是 App Router 不允許兩個 route group 對應到同一個 URL。C 讓新版頁面擁有自己的 root layout，從 <html> 開始就只載入新 design system 的 CSS。

代價：rewrite 會讓 server 端看到的 pathname（/v2/jobs）和瀏覽器看到的（/jobs）不一樣，造成 hydration mismatch 和 analytics 路徑錯誤。另外，有人直接打 /v2/... 的路徑時，也要導回乾淨的 URL，並且告訴搜尋引擎不要收錄。這兩個問題的解法在第五篇。

回頭看：rewrite 的副作用是可以一次性解決的；在 A 的做法下，CSS 污染是每一頁都要重新面對的。

3. 新舊並存多久

情境：新版上線後，舊版要留多久？

選項：

  • A. 新版上線就刪舊版，乾淨俐落
  • B. 舊版一直留著，當作長期的 rollback 方案
  • C. 舊版保留一段時間，真實流量跑過、確認沒問題就刪

選擇：C，目標是一週內刪除。這幾個核心頁面修改頻率很高，舊版留越久，越容易有人誤改到舊檔案。

實際上依頁面而不同：dashboard 在上線時就刪掉舊版，出事只能靠 git revert；職缺詳情大約兩週後刪除；職缺列表的舊版因為還有其他用途，到現在仍保留，隨時可以用 feature flag 切回去。

代價：保留期間，兩個版本都要維護。保留 rollback 路徑本身也有效能成本：量測時發現有一頁因為保留了舊版的 modal 當作 rollback，把整包舊 CSS 一起載回來，CSS 反而比舊版還大（第三篇）。

回頭看：會做一樣的選擇。真實流量跑過一輪、event 量比對完，就沒有理由再留。比較意外的是保留期間的效能成本，下次會把它算進「要留多久」的考量裡。

4. 多個頁面共用的大功能：在核心頁面一起重寫，還是先從邊緣頁面開始

情境：履歷編輯器和求職信編輯器是很大的功能：就地編輯、拖拉排序、新舊版本比對、下載、自動儲存，身上還掛著大量 tracking event。而且不只一個頁面在用：設定頁裡的「針對職缺優化過的履歷」列表會打開它們，核心的職缺詳情頁在申請流程裡也會打開它們。核心頁面的編輯器一壞，使用者就沒辦法順利申請職缺。

選項：

  • A. 等到重構核心頁面時，連同編輯器一起重寫、一起上線
  • B. 先在一個壞掉也不會影響核心流程的頁面上線新版編輯器，穩定後，核心頁面再用同一套新版編輯器、同樣的方式替換

選擇：B。

flowchart TD
    A["挑一個壞掉也不影響核心流程的頁面<br/>設定頁的優化履歷列表"] --> B["在這個頁面上線新版編輯器<br/>舊版保留，用 feature flag 切換"]
    B --> C["真實流量跑一段時間<br/>修掉問題、確認 event 都正常"]
    C --> D["核心的職缺詳情頁<br/>換上同一套新版編輯器<br/>同樣新舊並存、可以隨時切回舊版"]
    D --> E["穩定後刪除舊版與 flag"]

實際的順序是：設定頁先換上新版編輯器，大約三週後，核心的職缺詳情頁才換上同一套。這三週裡修掉的問題，例如分頁看起來同時被選取、錯誤訊息顯示在錯的位置、event 重複送出，都發生在不影響申請流程的地方。

新版編輯器一開始也不是全部重寫：外殼、分頁和比對畫面是新設計，資料流、API、自動儲存和 tracking event 沿用舊版的做法；還沒重做的分頁，先把舊元件「寄宿」在新版的 modal 裡，幾天後才換成新版。

這也是整個改版上線的共通模式：功能上線時，舊版和新版並存，用 feature flag 切換，出問題可以隨時切回舊版。例外是比較簡單、影響小、把握度高的功能，例如設定頁裡那幾個表單頁面，上線時就直接移除舊設計。

代價：

  • 並存期間，兩套編輯器都要維護，每個 tracking event 都要逐項對齊，並寫測試當作驗收依據
  • 為了 rollback 保留的舊版 modal 有效能成本：它把整包舊 CSS 一起帶進設定頁，就是第三篇「陷阱一」那個 CSS 反而變大的頁面
  • 過渡期的新版 modal 裡混著舊版的分頁，看得到新舊混合的痕跡

回頭看：會做一樣的選擇。核心頁面換上新版編輯器的時候，它已經在真實流量下跑過三週，最容易出錯的地方都先在邊緣頁面被抓出來了。如果選 A，這些問題會全部集中在核心頁面上線的那一天。

流程上的取捨

5. 追最新設計，還是凍結版本

情境：改版進行到後期，需求方持續針對新設計提出新想法，設計師也持續更新設計稿。開發的速度追不上設計的速度。

選項：

  • A. 一直追最新的設計稿
  • B. 凍結某一個版本，先把這個版本做完上線，新的設計排到之後

選擇：B。凍結前，先把設計稿和現況的差異分成三類，再跟需求方對齊（分類方式見第三篇〈設計稿追不上：凍結版本〉）。

代價：使用者短期內看不到最新的設計；需求方也要接受「這個想法要等下一版」。

回頭看：會做一樣的選擇，而且應該更早做。凍結之後，不用同時維護兩個設計版本，開發的節奏也終於穩定下來。

6. 新需求加在舊頁面，還是新頁面

情境：重構期間，產品還在迭代。新需求進來時，該加在現在線上的舊版，還是正在開發的新版？

選項：

  • A. 全部加在新版，舊版凍結
  • B. 全部加在舊版，新版完成後再搬
  • C. 依頁面狀態決定

選擇：C。還沒開始重構的頁面，照常加在舊版；正在重構的核心頁，其他工程師繼續改舊版，最後短暫停工同步（流程見第三篇）。

代價：同一個需求可能要做兩次；停工期間其他人的開發會被卡住幾天。

回頭看：A 會讓重構變成其他人的阻礙；B 在核心頁面上會讓新版永遠追不上舊版。C 的成本是幾天的停工，換到的是重構不會被無限延長。

7. 部分頁面保留舊版，不追求全部刪乾淨

情境：原本的目標是所有頁面都搬到新版，然後整包移除 Bootstrap 和舊的 UI library。

選擇：部分未登入頁面因為其他業務需求，刻意保留舊版；少數流程頁面也還沒搬。

代價：舊的 UI library 到現在一個都還沒能移除，repo 裡的舊 CSS 總量幾乎沒變。這次量到的改善，是「新版頁面實際載入的樣式」，不是「整個 repo 的程式碼量」。

回頭看：改版的目標是讓使用者看到的頁面變好、讓之後的開發變快，而不是 repo 裡的數字好看。剩下的頁面等有明確的商業理由時再搬。

程式碼組織上的取捨

8. 共用元件什麼時候抽

情境：19 個頁面裡有很多看起來相似的區塊。要一開始就全部抽成共用元件，還是等需要時再抽？

選項：

  • A. 一開始就抽：先盤點所有頁面，把相似的部分都做成共用元件
  • B. 第二個使用者出現時才抽（promotion rule）：新元件先放在頁面旁邊，第二個頁面需要時，在同一個 PR 裡把它搬到共用目錄

選擇：階段 0 切元件時用 A，正式搬遷時用 B。

階段 0 的目的是把設計稿切成一套 component library，所以讓 AI 先分析設計稿、盤點共用元件，再由我判斷哪些合理。正式搬遷時，真實資料和真實需求會讓很多「看起來一樣」的元件變得不一樣，這時就改用 B，並且定了三條規則：

  • 有業務語意的元件（例如職缺卡片）搬到對應的 domain 目錄
  • 沒有業務語意的元件（例如按鈕、modal）搬到 design system，並且補一個 Storybook story
  • 把一段 JSX 複製到第二個頁面，不被接受

這三條在 10 月初寫進 DESIGN.md，以及 AI agent 每次開工都會讀的專案規則檔，人和 AI 照同一套規則抽元件（AI 怎麼守規則，見第四篇的「三層機制」）。

整個新版程式碼的依賴方向只能由上往下：

flowchart TD
    P["Page<br/>頁面本身與只有它用到的元件"] --> S["Shell<br/>root layout、側欄、header"]
    P --> C["Domain 元件與 headless hooks<br/>職缺卡片、申請表單、業務邏輯"]
    C --> DS["Design system<br/>Button、Modal、Tabs 等無業務語意的元件"]
    S --> DS
    DS --> T["Design tokens<br/>顏色、字級、圓角、尺寸、斷點"]

依賴方向正確，改一個元件不是也會影響好幾頁？

會，而且這是刻意的。把按鈕抽成共用元件，目的就是改一次、所有頁面一起變。

依賴方向要保證的是另一件事：看檔案放在哪一層，就能判斷改它會影響誰。

  • 改頁面裡的檔案：只有這一頁會變
  • 改 domain 元件：用到這個元件的頁面會變
  • 改 design system：所有頁面都可能變

方向反過來時，這個判斷就失準了。我後來抽查時發現一個「履歷拖放上傳區」元件放在設定頁的資料夾裡，看起來是設定頁私有的，但 Dashboard、職缺列表與職缺詳情頁的上傳 modal、自動申請的設定流程都在用它。用三個假設的修改來比較：

修改 檔案放在 從位置判斷會影響 實際會影響
按鈕的圓角從 8px 改成 12px Design system 所有頁面 所有頁面，符合預期，可以在 Storybook 逐一檢查
職缺卡片的薪資移到標題下方 Domain 層 有職缺卡片的頁面 同左，符合預期
設定頁希望上傳完成後直接跳到履歷列表，改的人把跳頁寫進這個元件 設定頁的資料夾 只有設定頁 設定頁、Dashboard、職缺列表與職缺詳情頁的上傳 modal、自動申請設定流程

前兩個修改也會讓好幾頁一起變，但改的人事先就知道，會去檢查所有用到的地方。第三個需求只對設定頁合理，但改的人照位置判斷只測了設定頁，結果使用者在職缺頁面補一份履歷，上傳完就被帶離那個職缺。這些都在核心流程上。

修法是照 promotion rule 把它搬到 domain 層。影響範圍沒有變小，改它一樣會影響這幾個地方；差別是改的人一看位置就知道它是共用的。

依賴方向還有第二層意義：越底層的東西被越多地方依賴，越不該隨便改，也需要越多保護。Design system 的每個元件都有 story，domain 元件有測試，頁面則是需求最常落下來、改得最頻繁的地方。方向正確時，頁面怎麼改都不會往下傳；方向反過來，頁面為了自己的需求所做的每次修改，都可能傳到別的頁面去。

位置判斷只是第一道防線。專案裡另外有一支影響範圍分析的腳本，從相依圖算出改一個檔案會影響哪些頁面，並提醒改了共用元件要回頭補 story。依賴方向讓人光看位置就能大致判斷，腳本負責給出精確的答案。

代價：B 需要紀律。規則是靠 code review、文件和 AI 的規則檔守住的，不是工具強制的；上面那個拖放上傳區，就是我後來抽查時才發現的。

回頭看：會做一樣的選擇，但會更早把依賴方向寫成 lint 規則，而不是只靠 review。

這個拖放上傳區修正前後的依賴圖、違反方向的兩種情況，以及元件的依賴怎麼設計，我另外整理成一篇：前端元件的依賴方向：改一個檔案，為什麼會影響到不相干的地方。

9. 不寫 barrel index.ts

情境：很多專案會在元件目錄放一個 index.ts，它不寫任何邏輯，只把同目錄的元件 re-export 出去，讓別的檔案從同一個入口 import。這種檔案叫 barrel file：

選擇：共用元件一律 import 單一檔案，不寫 barrel。頁面私有的元件則用相對路徑 import。

代價：import 路徑比較長，一個檔案開頭可能有好幾行 import。

回頭看：好處比代價大很多：

  • 一行 grep 就知道誰在用某個元件，刪除或修改前的影響範圍分析變得很簡單。例如要改 Button，grep -r "design-system/Button" 就能列出所有使用的地方；如果大家都寫 from '@/design-system'，路徑裡看不出是哪個元件，只能改搜 Button，結果會混進 ButtonGroup、其他套件的 Button，還得一個一個排除
  • 看到相對路徑就知道這是頁面私有的，改它不會波及別的頁面
  • 對 AI agent 也比較友善：它不用追 barrel 的 re-export 鏈，就能找到元件的實際位置

總結

# 取捨 選擇 主要代價 重來一次
1 整頁重構 vs 逐步替換 整頁重構 單一 PR 大、修改要搬兩次 一樣
2 新舊並存的方式 middleware rewrite pathname 不一致的副作用 一樣
3 新舊並存多久 目標一週，依頁面調整 保留期間的維護與效能成本 一樣，但把效能成本算進去
4 多頁共用的大功能 先從邊緣頁面上線，再換核心頁面 兩套並存的維護與效能成本 一樣
5 追設計 vs 凍結版本 凍結 新設計要等下一版 一樣，而且更早做
6 新需求加在哪 依頁面狀態決定 部分需求做兩次、短暫停工 一樣
7 是否全部刪乾淨 保留部分舊頁面 舊 UI library 還不能移除 一樣
8 共用元件什麼時候抽 第二個使用者出現才抽 需要紀律，靠 review 守 一樣，但更早寫成 lint
9 barrel index.ts 不寫 import 路徑較長 一樣

九個取捨的方向，回頭看幾乎都不會改；會改的是時間點。凍結版本、把舊版的成本算清楚、把規則寫成工具，這三件事如果早一點做，後面會少很多來回。
