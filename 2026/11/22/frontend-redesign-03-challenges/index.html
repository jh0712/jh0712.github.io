前端改版實戰（三）：挑戰與解法，從 CSS 耦合到量測後才發現的效能陷阱

這是「前端改版實戰」系列的第三篇。前兩篇講了 Remote Hunter 改版的過程與取捨，這篇整理過程中真正卡住我的五個挑戰：兩個是技術問題，另外三個是人和流程的問題。

系列文章：（一）整個過程、（二）Trade-off、（三）挑戰與解法、（四）用 AI 加速、（五）技術補充

挑戰一：CSS 耦合到改不動

問題

舊系統同時混用 Bootstrap、Tailwind CSS 和兩套 UI library，再加上將近五萬行的 SCSS。前人為了在某一頁調整樣式，常常用 !important 蓋掉 Bootstrap 或 UI library 的預設值，久了就變成一層蓋一層。

實際量測職缺列表頁載入的樣式表：上萬條 CSS rule、接近三千條 !important、113 種字級。在這種狀態下，新元件只要放進舊頁面，就會被全域樣式影響。

解法：從 root layout 就把 CSS 樹切開

Next.js App Router 允許有多個 root layout。我讓新版頁面擁有自己的 root layout，從 <html> 開始就是一棵獨立的樹：

flowchart TB
    subgraph Legacy["舊版樹"]
        LR["舊版 root layout"] --> LC["Bootstrap<br/>舊 UI library<br/>SCSS<br/>舊版 Tailwind 設定"]
        LR --> LP["舊版頁面"]
    end
    subgraph New["新版樹"]
        NR["新版 root layout"] --> NC["新版 Tailwind 入口<br/>design tokens"]
        NR --> NP["新版頁面"]
    end
    Shared["共用基礎設施<br/>狀態管理、API client、analytics"] --> LR
    Shared --> NR

規則很簡單：

  • 新版頁面不可以 import 任何舊版元件、Bootstrap 或舊版的 Tailwind 入口
  • 兩個 Tailwind 入口永遠不互相 import
  • 狀態管理、API client、analytics 這些和樣式無關的基礎設施，兩棵樹共用，不複製一份

再加上 middleware rewrite（第二篇、第五篇），同一個 URL 就可以依條件交給其中一棵樹處理。

結果是新寫的程式碼裡 !important 只剩兩個，都是 prefers-reduced-motion 的覆寫；新版頁面載入的樣式表，!important 減少 92%，字級從 113 種收斂到 28 種。

挑戰二：重構途中，需求和設計一直在變

部分首頁畫面要維持現狀

重構進行到一半時，需求方決定部分首頁畫面先維持現狀，不直接被新設計取代。

這個問題反而不難，因為新版架構本來就是用 feature flag 控制每個頁面要走新版還是舊版。我做的是：

  • 用一份設定描述哪些首頁畫面走新版、哪些保留舊版
  • 之後要調整，只需要改設定，不需要動頁面本身

當上線機制本來就是以頁面和 flag 為單位設計的，中途改需求的成本就會很低。

設計稿追不上：凍結版本

比較麻煩的是改版後期：需求方持續針對新設計提出新想法、嘗試新頁面，設計師也持續更新設計稿。結果是正在開發的版本，永遠追不上最新的設計。

我先把最新設計稿和目前開發中的版本逐項比對，把每一項差異分類：

flowchart TD
    D["新設計稿裡的一項差異"] --> Q1{"現有系統<br/>有這個功能嗎？"}
    Q1 -- "沒有" --> F["新功能<br/>排到重構之後，另外規劃"]
    Q1 -- "有" --> Q2{"需要改資料流<br/>或後端 API 嗎？"}
    Q2 -- "需要" --> C["既有功能調整<br/>評估影響，跟需求方確認優先順序"]
    Q2 -- "不需要" --> V["純畫面調整<br/>成本低，直接放進這一版"]

分類完再跟需求方和設計師討論，確認大家的商業目標一致，然後凍結一個版本先做完。

這裡也用了「漸進式價值交付」的想法：使用者先拿到新畫面，享受到新 UI 的好處；同時我們有更多時間準備複雜的功能和新需求，一點一點把完整的功能交付出去。

挑戰三：多位工程師同時在改同一個核心頁面

問題

最後三個核心頁面裡，有一頁是產品正在快速迭代的功能，好幾位工程師同時在改這一頁。

受限於挑戰一提到的 CSS 耦合，這一頁沒辦法小範圍逐步搬遷，只能整頁重構。如果我在重構期間要求大家停止修改，會卡住所有人好幾週；如果不停，新版永遠追不上舊版。

解法：平行開發，最後短暫停工同步

sequenceDiagram
    participant O as 其他工程師
    participant L as 舊版頁面
    participant Me as 我
    participant N as 新版頁面
    Me->>O: 說明預計完成時間，以及哪些模組完成後才能在新版開發
    par 平行開發
        O->>L: 繼續開發新需求
    and
        Me->>N: 整頁重構
    end
    Me->>O: 新版完成，請暫停修改 3 到 5 天
    Me->>N: 把舊版這段期間的新需求補進新版
    Me->>N: 上線新版，舊版保留當 rollback
    Note over L,N: 過渡期：AI 的 system prompt 加上規則，提醒同時維護兩頁
    Me->>L: 確認沒問題後刪除舊版
    O->>N: 之後的新需求都在新版開發

幾個關鍵細節：

  • 先溝通時程與模組順序：讓大家知道我預計什麼時候完成，以及哪些模組完成之前，新功能請先做在舊版
  • 停工時間盡量短：只在最後同步的那幾天請大家暫停，而不是整個重構期間
  • 讓 AI 也知道過渡期的規則：我在專案的 system prompt 裡加上暫時性的提醒，讓大家使用 AI 開發時，AI 會知道這段期間要同時維護兩頁
  • 盡快刪除舊版（理由見第二篇）

挑戰四：怎麼在短時間內驗證，並安全刪掉舊頁面

問題

這是整個改版最有挑戰性的部分。核心頁面身上掛著大量的 tracking event，任何一個 event 掉了，產品端的數據就會出問題，而且可能好幾天後才被發現。

解法：event inventory + local e2e 驗證與測試 + 分波上線 + 刪除前的反向依賴分析

每一頁都照同一個流程走：

flowchart TD
    A["開工前：event inventory<br/>列出這一頁所有 tracking event"] --> B["開發新版頁面"]
    B --> C["local 驗證：e2e 走完整個流程<br/>逐條確認 event 都有觸發"]
    C --> T["寫測試保護這些流程與 event<br/>PR 描述列出保留的 event"]
    T --> D["上線新版"]
    D --> E{"上線後比對 event 量<br/>有沒有掉？"}
    E -- "有異常" --> F["rollback<br/>修正後再上"]
    F --> D
    E -- "正常" --> G["真實流量跑過一輪"]
    G --> H["刪除前跑反向 import 分析<br/>確認沒有其他地方還在用"]
    H --> I["另開 PR 刪除舊頁面"]

以 dashboard 為例，開工前列出了十幾個 event。開發完成後，先在 local 用 e2e 把這一頁使用者會走的流程完整跑一遍，對照 inventory 逐條確認每個 event 都有觸發。接著把這些流程和 event 寫成測試保護起來：之後不管是誰、哪個 agent 改到這一頁，event 掉了測試會先失敗，不用等到上線後看數據才發現。

核心頁面的上線順序是 dashboard → 職缺詳情 → 職缺列表（登入）→ 職缺列表（訪客），每一波之間都會比對 event 量，確認沒問題再進下一波。每一波的 rollback 方式不一樣：上線時就刪掉舊版的頁面，只能用 git revert；還保留舊版的頁面，用 feature flag 立刻切回去。

另外還有一個自動化的檢查：新舊兩個 root layout 必須掛同一組 analytics 元件，有一支檢查腳本禁止任何一邊自己另外掛 tracker。這樣不管頁面走哪一棵樹，tracking 的行為都一樣。

挑戰五：量測之後才發現的效能陷阱

問題

頁面搬完之後，我原本以為效能自然會變好。實際用同一套方法量測新舊兩個版本後，大部分的頁面確實大幅改善，但有幾頁的數字反而變差，原因都藏在新舊並存的細節裡。

陷阱一：保留的 rollback 路徑，把舊 CSS 一起載回來

有一頁的 CSS 下載量，新版反而比舊版多了約 5%。追下去發現：這一頁為了 rollback，保留了一個舊版的 modal。只要這個 modal 的程式碼還在 import 鏈上，打包工具就會把它依賴的整包舊 CSS 一起帶進來。

刪掉這條 rollback 路徑之後，這一頁的 CSS 下載量從比舊版多 5%，變成比舊版少 74%。

陷阱二：新版頁面偷偷 prefetch 了舊版頁面

另一個例子更隱蔽。新版的側欄上有一個連結，指向一個還沒搬遷的舊版頁面。Next.js 的 <Link> 預設會在連結出現在畫面上時 prefetch 目標頁面，而這個側欄掛在每一個登入後頁面上。

結果是：每一個新版的登入後頁面，在瀏覽器端都會額外下載一整包舊版 CSS。其中一頁在手機情境的 load 時間，甚至比舊版慢了 58%。

這個問題在靜態分析（看打包結果）時完全看不出來，因為那份 CSS 不屬於這一頁的 bundle，只有在真實瀏覽器裡量測下載了哪些資源，才會發現。

修法很簡單：把所有指向舊版頁面的 <Link> 都關掉 prefetch。修完之後，新版頁面在瀏覽器裡終於只載自己的樣式；那一頁手機情境的 load 時間，從比舊版慢 58% 變成快 14%。

陷阱三：有些指標新舊版不能直接比

有一頁的 LCP（最大內容繪製時間），新版看起來比舊版慢。追下去發現，兩個版本的 LCP 量到的是不同的東西：

  • 舊版的標題字比較大，標題一畫出來就成為 LCP 元素，之後出現的內容都比它小
  • 新版的標題比較小，等資料回來、畫出內容卡片後，LCP 才落在那張卡片上

也就是說，舊版的 LCP 量的是「標題畫出來」，新版量的是「資料到齊」。兩者不可比，而新版的 FCP（首次繪製）其實比舊版更早或相同。

量測也找到幾個還有待處理的效能項目，根因大多不在新版設計，而在既有的資料載入方式，已經列進待處理清單。

心得

「搬完」不等於「變快」。新舊並存的過渡期，最容易藏著意想不到的成本：保留的 rollback 路徑、指向舊頁面的連結、還沒搬完的共用元件，都可能把舊的東西帶回來。要知道新版有沒有真的變好，只能量。這些例外是怎麼被抓出來的，第四篇會講。

總結

挑戰 類型 解法的核心
CSS 耦合 技術 從 root layout 切開兩棵 CSS 樹
需求和設計一直在變 流程 呈現方式抽成設定；差異分類後凍結版本
多人同時改同一頁 協作 平行開發，最後短暫停工同步
安全刪除舊頁面 風險控管 event inventory、local e2e 驗證與測試、分波上線、反向依賴分析
量測後才發現的陷阱 技術 用真實瀏覽器量測，逐一追根因

回頭看，五個挑戰裡只有兩個是純技術問題，其他三個靠的是同一件事：跟需求方、設計師、合作的工程師來回溝通，把「版本」的概念帶進來，決定這一版做到哪、下個需求排在哪一版、功能上下線的順序。

大型重構的難點通常不在程式碼，而在怎麼讓重構和產品的日常迭代同時進行。
