前端改版實戰（一）：19 個頁面、六週，從 Bootstrap 大雜燴到 Design System

這是「前端改版實戰」系列的第一篇。我花了大約六週，把 Remote Hunter 的 19 個頁面從舊設計搬到新的 design system。過程中新舊頁面一直並存，使用者無感切換，最後再把舊頁面安全刪掉。這篇先講完整的過程與成果，後面幾篇再分別談取捨、挑戰、AI 的用法，以及值得記下來的技術細節。

（實作時間：2026-08-31 ～ 2026-10 中）

系列文章：（一）整個過程、（二）Trade-off、（三）挑戰與解法、（四）用 AI 加速、（五）技術補充

背景：一個 CSS 改不動的專案

Remote Hunter 是一個 to C 的遠端工作求職網站，使用者可以搜尋職缺、用 AI 優化履歷，並且快速送出申請。前端是 Next.js，早期為了快速驗證市場，開發速度優先於程式碼品質，經過幾年的快速迭代，樣式層變成這樣：

  • Bootstrap、Tailwind CSS、兩套 UI library 同時存在，再加上將近五萬行的 SCSS
  • 大量 !important：以職缺列表頁為例，實際載入的樣式表裡有接近三千條 !important 宣告。前人為了蓋掉 Bootstrap 或另一套 library 的樣式，只能一層一層往上疊
  • 113 種不同的字級：沒有人刻意設計，只是每次改版都多加一種

結果是：改一個按鈕的顏色，要先追三層 override；在某一頁修好的樣式，可能在另一頁壞掉。

剛好這時設計師交付了一份新的 design prototype（HTML 設計稿），目標是統一整個產品的視覺，並且建立一套之後可以持續重用的 component library。

評估後發現，舊的全域樣式會污染新元件，新元件放進舊頁面，要長成設計稿的樣子只能再疊 !important。所以改成以頁面為單位整頁重構，新舊頁面用完全分開的 CSS 樹，使用者看到的 URL 不變，背後依 feature flag 決定走新版還是舊版（取捨見第二篇）。

前置作業：先把雜訊清掉

在動手重構之前，我先做了兩件看起來跟改版無關的事：

  1. 清理 dead code：213 個檔案、約一萬四千行，其中 68 個是完全沒被引用的檔案（詳見 Dead Code 清理實戰）
  2. 清理沒有入口的 route，並盤點 log 與 tracking：確認哪些頁面真的還有人在用、哪些 event 是有人在看的（詳見 Route 清理實戰）

這兩件事對改版的價值是：

  • 縮小重構範圍：已經沒人用的頁面不用搬
  • 減少 AI agent 誤判：這次大量使用 AI coding agent，舊程式碼越少，agent 越不容易讀到過時的元件而跟著改錯，token 也用得比較少
  • 知道哪些 event 不能掉：之後每搬一頁，都要確認 tracking 沒有少

這張時程表是事後整理的。元件和架構在 8 月中就完成了，正式搬進專案是從 8 月底開始，到 10 月中刪掉最後一個舊的核心頁面，大約六週。

實際上不是一開始就規劃好六週的計畫，而是邊開發邊規劃：每完成一個階段，就根據遇到的問題修正下一階段的計畫文件。中途也有新的商業需求插進來，例如決定部分首頁畫面先維持現狀。

階段 0：把 HTML 設計稿切成 React 元件，定下前端架構

設計師交付的 prototype 是一份 HTML 設計稿：畫面都有了，但只是靜態的 HTML 和 CSS，沒辦法直接放進正式專案。所以階段 0 要做兩件事：照著設計稿把 HTML 切成 React 元件，同時定下之後新版前端的架構。

我用 AI 開了一個獨立的新專案來做這件事，需求只有幾條：

  • 使用 Next.js 16 和 Tailwind CSS
  • 把設計稿裡重複出現的部分拆成共用元件
  • 每個元件都要有 Storybook story，方便之後搬到正式專案時套版
  • 產生一份 DESIGN.md，記錄 design token、元件目錄與使用規則

大約兩個工作天，產出了：

項目 數量
頁面 19 頁（9 個行銷頁、10 個登入後頁面）
共用元件 約 70 個
Storybook story 約 190 個

元件怎麼分層、design token 怎麼定義、新版程式碼要遵守哪些規則，都是在這個階段定下來的，之後搬進正式專案就以這套元件和規則為基礎。

不過 AI 切出來的東西不能直接用。有些頁面內容是 AI 自己編的，跟設計稿對不上；頁面一多，AI 也開始偷懶。這部分的細節和我後來調整的做法，留到第四篇再談。

我先一頁一頁對齊設計稿，再請設計師核對。設計師在 web 與 mobile 兩種尺寸下一共找出 44 處與設計不符的地方，全部修正後，這套元件就定案，成為之後搬進正式專案時的標準。

架構一句話版

正式專案的做法是讓新舊兩套頁面並存：

flowchart LR
    U["使用者請求 /jobs"] --> M{"middleware：<br/>這個 route 要走新版嗎？"}
    M -- "是" --> N["內部改寫到 /v2/jobs<br/>新版 root layout<br/>只載入新 design system 的 CSS"]
    M -- "否" --> O["維持 /jobs<br/>舊版 root layout<br/>Bootstrap 與舊 UI library"]
    N --> R["瀏覽器網址列<br/>永遠顯示 /jobs"]
    O --> R

（這是簡化版，完整的判斷順序見第五篇。）

  • 使用者永遠看到同一個 URL，middleware 依 feature flag 與使用者狀態，決定要把請求交給新版或舊版的頁面
  • 新版頁面有自己的 root layout 和 CSS 入口，完全不載入 Bootstrap 與舊的 UI library
  • 遷移一頁 = 新增一個新版 page + 在 route 清單加一行設定，不需要改部署設定

這個架構讓每一頁都可以獨立上線、獨立 rollback。

遷移順序：從低風險到高風險

排順序有兩個原則：

  • 先做風險低、複雜度低的頁面，把元件庫和流程磨熟，再碰核心功能
  • 漸進式價值交付：每一個階段都讓使用者先拿到看得到的改善，而不是等全部做完才一次上線
階段 頁面類型 為什麼排這個順序
1 未登入的行銷頁（首頁、FAQ、條款、聯絡我們等 9 頁） 幾乎都是靜態內容，沒有使用者資料，出錯影響小；新畫面對 conversion 有直接幫助
2 登入後的設定與 CRUD 頁（個人資料、求職追蹤、履歷設定、職缺通知等） 開始串後端 API，但元件組合單純，可以驗證「新元件 + 真資料」的模式
3 核心功能頁（dashboard、職缺列表、職缺詳情） 元件組合最複雜、tracking 最多、多位工程師同時在改，留到最後

前兩個階段大致照計畫走。真正花心力的是最後三個核心頁。

最後三個核心頁怎麼上線

這三頁有幾個特性：產品還在快速迭代、多位工程師同時在改同一頁、身上掛著最多的 tracking event。處理方式大致是：

  • 凍結設計版本：跟需求方和設計師討論後，先凍結一個版本做完重構，新需求排在重構之後
  • 跟其他工程師協調：他們繼續改舊版，我同步做新版，最後短暫停工同步
  • event inventory + 分波上線 + 保留 rollback：開工前列出所有 tracking event，上線後比對 event 量，真實流量跑過一輪才刪舊版

其中最有挑戰的，是怎麼在短時間內驗證新版，並安全刪掉舊版。這幾件事的細節都在第三篇。

新版的改變不只是換顏色：

  • 卡片的資訊層級重新整理：公司 logo、職稱和公司名稱排在一起，薪資、地點、一鍵申請這些標籤放在固定位置，描述縮成兩行
  • 主要動作直接放在卡片上：舊版的卡片只有資訊，新版把 View Details、Pass、Apply 三個按鈕放進卡片，手機版也收斂成同一排按鈕
  • 篩選 modal 改成比較寬、比較密的版面：拿掉藍色標題列，每個區塊的「Select any」對齊到右側，打開後第一個畫面就能看到經驗、薪資這些原本要往下捲才看得到的篩選條件
  • 登入後的導覽從上方 top bar 改成左側 sidebar：舊版的導覽、升級按鈕、電話和帳號都擠在頂端一排；新版改成可以收合的左側 icon sidebar，搜尋列直接移到最上方，內容區可以用的寬度變多
  • 履歷編輯從全螢幕改成置中的 modal：舊版點開是整個畫面覆蓋、藍色的分頁列；新版是置中、圓角、背景變暗的 modal，分頁改成 segmented control，下載按鈕放在右上角

改善了多少

以下數字都是在同一台機器、本地環境下量測，只比較新舊版本的相對差，絕對值不能直接對應 production。量測方法見第五篇。

指標 改善
每頁 CSS 下載量 −76% 到 −80%
職缺列表頁載入的樣式表：rule 數 −85%
職缺列表頁載入的樣式表：!important −92%
唯一字級數 113 → 28
每頁總下載量 −5% 到 −72%（首頁 −72%，行銷頁約 −50%）
手機情境（slow 4G + 4× CPU 節流），dashboard 等三個登入後頁面的 load 時間 從 20 秒級降到 4 到 8 秒
同上三頁的 Total Blocking Time −70% 到 −78%
同上三頁的版面跳動（CLS） 從 0.3–0.7 降到 0.1 以下
dashboard 的 JS heap 67 MB → 23 MB

新寫的程式碼裡，!important 只剩兩個，都是為了 prefers-reduced-motion 的覆寫。

不是每個指標都變好。主執行緒的負擔整體大致持平，少數頁面還有待處理的效能項目；也有幾頁在量測後才發現反而變差，追根因後修掉了（第三篇）。

還沒完成的

  • 少數流程頁面還在舊版，所以舊的 UI library 目前一個都還沒能移除，要等全部頁面搬完才能整包拿掉
  • 部分未登入頁面因為其他業務需求，刻意保留舊版，不在這次範圍內

已經搬完的頁面，新功能都直接在新版上開發。

三個心得

  1. 前置清理比想像中重要：dead code 和 route 清理看起來跟改版無關，但它讓重構範圍變小，也讓 AI agent 少犯錯
  2. 順序就是風險控管：先做靜態頁，把元件庫和上線流程磨熟，最後才碰核心頁。到了核心頁時，要處理的只剩真正困難的部分
  3. 「搬完」不等於「變快」：有幾頁量完反而變差，原因都在新舊並存的細節裡。沒有量測，就不會知道（第三篇）

系列導讀

  • 第一篇（本篇）：整個過程與成果
  • 第二篇：Trade-off：整頁重構還是逐步替換、新舊並存多久、共用元件什麼時候抽，以及其他我放棄了什麼
  • 第三篇：挑戰與解法：CSS 耦合、需求和設計一直在變、多人同時改同一頁、安全刪掉舊頁面、量測後才發現的效能陷阱
  • 第四篇：用 AI 加速：切元件時給 AI 的 prompt、AI 一次能做幾頁、4 到 5 個 agent 平行開發與自動驗證、讓 AI 協助量測成效
  • 第五篇：技術補充：middleware rewrite、Tailwind v4 design token、headless hooks、前端重構的量測方法
