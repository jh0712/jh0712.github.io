用 AI Agent 加速驗證 MySQL DDL：從一段 prompt 到可重現的實測報告

「大表加欄位會鎖表」這種問題，真要驗證是很痛的：要準備 100 萬筆資料、要跑十幾個情境、其中好幾個單一 ALTER 就跑一兩個小時，而且你得全程盯著寫入有沒有被擋。光是最後報告裡那幾個大 ALTER 的實測時間加起來就超過 4.5 小時，還不含灌資料。這種「大量等待 + 機械操作 + 但需要判斷」的任務，正好是 AI agent 最划算的應用場景。這篇不談 MySQL 的結論（那在 另一篇），只談方法：怎麼寫 prompt、怎麼讓它的結論可被驗證、以及哪些部分不能交給它。

這類任務為什麼適合丟給 agent

先說清楚：這不是「問 AI 要答案」

「大表加欄位會不會鎖表」這種問題，現在直接問 AI 幾秒鐘就有答案，而且方向通常是對的。但它給的是 MySQL 手冊層級的通用結論——你那張表實際會怎樣，取決於它有沒有 FULLTEXT、INSTANT 額度剩幾次、是哪個小版本、過去被改過什麼。尤其是從舊版本一路升上來的 production 表，殘留狀態不會寫在任何文件裡，AI 也無從知道。

所以這次的用法是反過來的：不是問 AI 要結論，而是讓 AI 去跑實驗、把我們這套系統的實際規則量出來。 AI 負責執行和舉證，結論由數據決定。

四個判準

我挑任務給 agent 跑的判準一直是這四個，DDL 驗證四個都滿分：

  • 大量等待：單一情境動輒 1～2 小時，人不可能盯著。但 agent 可以一邊等一邊寫報告。
  • 步驟機械、但需要臨場判斷：看 processlist、算耗時、決定某個跑太久的 ALTER 要不要 KILL——這些用腳本寫死很麻煩，但對 agent 很自然。
  • 驗證成本低：每個結論都是一段 SQL，我要抽查只要複製貼上重跑一次。這是關鍵——AI 產出的價值不在於它說了什麼，而在於它的說法能不能被便宜地驗證。
  • 風險可控：整輪都在 local docker 的複製表上，錯了 DROP TABLE 重來。

反過來說，如果一個任務的結論無法用一行指令驗證，把它丟給 agent 通常是在替自己製造工作。

Prompt 的六個區塊

這次用的 prompt 不長，但每一段都在解決一個特定的失敗模式。完整原文在文末附錄，這裡拆開講為什麼要那樣寫。

1. 先圈出技術邊界

我目前 backend 有 mysql docker，此次測試使用純 sql 語法進行測試，不要用到 laravel 的 Item eloquent model 避免觸發相關排程。

不講清楚的話，agent 看到一個 Laravel 專案會很自然地用 Eloquent 和 factory 來灌資料——而這張表是 items，碰到 model 就可能觸發 queue 排程。「不要用什麼」跟「要用什麼」一樣重要，尤其是那種「執行起來不會報錯，但會在別的地方出事」的做法。

2. 給前因，讓它知道你在追什麼

先前針對 items table create 新欄位會遇到 lock table 以及重建表的問題，有時候是 meta data lock，有時候是因為 fulltext index，有時候是新表建立外鍵的時候會鎖表 or 重建表。但是不清楚原因。每次都有相關事件記錄在專案 repo 中

這段是整個 prompt 裡投報率最高的。它做了三件事：限縮搜尋範圍（往這三個方向查）、指出可用的證據來源（repo 裡有事件記錄，agent 會自己去翻 migration 檔和 commit）、說明目的不是「跑測試」而是「找出原因」。

有前因的 prompt 和沒有的差別，是「它照著你列的清單做完」和「它會補你沒想到的情境」。

3. 量化模糊詞

等很久的定義是大於兩分鐘（久）、五分鐘（很久）的程度

「很久」「很慢」「太大」這種詞如果不定義，你會拿到一份用形容詞寫的報告，沒辦法拿去做決策。定義成兩個閾值之後，最後那張速查表每一列才有可比較的分級。

凡是最後會出現在結論裡的形容詞，都要在 prompt 裡給定義。

4. 把「已知」寫出來，但明說不可直接相信

目前已知（這些不可直接相信，需要先做測試）

  1. table 中如果有 fulltext index, 建立新欄位會重建表
  2. metadata change 超過 64 次，會需要重建表
  3. 有其他資料在寫入的時候，會需要等待
  4. 新的欄位如果有指定位置，會重建表

這是整段 prompt 裡我最想推薦的一招。

只給「已知」不加但書，agent 會把它當前提，然後去找支持的證據——你會拿到一份四條全部「✅ 確認成立」的報告，非常好看，但沒有價值。加上「不可直接相信」之後，這四條變成待驗證的假設，每一條都要有實測數據支撐。

結果是四條裡有一條（指定位置會重建表）被推翻了——那是 MySQL 8.0.28 以前的行為，我們的 8.0.46 早就不適用。如果沒加這句，這條過時知識會繼續被當成前提沿用，而且這次還會多一份 AI 報告幫它背書。

列出你以為你知道的事，然後要求 agent 試著推翻它。

5. 要求重現步驟，而不是只要結論

不同的情境：測試需要說明如何重現以及說明過程

這句話把產出從「一份要你選擇相信的報告」變成「一份可以抽查的報告」。最後每個情境都附了可以直接貼進 mysql client 的 SQL、實際的錯誤訊息、processlist 的狀態——我抽驗其中幾個只花了幾分鐘。

6. 講出真正的目的

主要目的：在後續對大表操作的時候，可以有一個警惕，避免 laravel migration 對表做操作的時候，過久等待的情況。

有這段，agent 知道要產出的是「migration 前的判斷依據」，所以最後主動把結論收斂成八條 Laravel migration 建議，而不是停在一堆 MySQL 行為的描述。說明用途，產出的形狀就會對。

另外我也留了一句開放的：「測試需要補其他常見操作」「可以測試多種組合」——留白讓它補我沒想到的情境（DROP INDEX、合併多欄位 ALTER、drop FULLTEXT 之後的殘留效應都是這樣冒出來的）。

讓結論可信的三個機制

prompt 寫得好只能讓它跑對方向，要讓結論能拿去做決策，還要有下面這幾件事。

探針：不要問 agent「有沒有鎖表」，要它拿出證據

這是整輪測試最重要的設計。「這個 ALTER 有沒有擋寫入？」如果讓 agent 用 processlist 目測或用知識回答，你拿到的是它的推論，不是觀測。

改成這樣：背景開一個迴圈，每 0.5 秒對測試表寫一筆，記錄每筆耗時；再開一個做點查 SELECT。

於是「加 FULLTEXT 會擋寫」這個結論的證據變成「寫入探針卡了 6,924.76 秒，讀取探針 13,556 筆全過、最慢 1.22 秒」。這是觀測值，不是推論；而且寫探針和讀探針分開，還意外釐清了「擋寫但不擋讀」這個關鍵區別。

一般化的原則：凡是要判斷「會不會影響服務」的測試，都先設計一個持續打流量的探針，用探針的延遲當作證據。

watchdog：給每個情境一個上限

有些操作是真的跑不完的（型別變更那個跑到 12 分鐘還停在 copy to tmp table）。事先約定好「超過 N 分鐘就 KILL 並記錄為 >Ns（被砍）」，agent 就不會卡在那裡空等，報告裡也能誠實標示這是下限而不是實測值。

這裡也有個需要人先確認的安全問題：KILL 一個進行中的 ALTER ... COPY 是安全的（只是丟棄 tmp table），但 KILL 一個大的 DML 交易完全不是——實測 rollback 花了 30 分鐘以上，而且期間鎖照樣持有。這種「哪些動作可以放心讓 agent 自己做」的界線，要在放它跑之前想清楚。

環境隔離與參數記錄

測試期間要停掉 queue worker 和 scheduler，不然 IO 干擾會讓數字失真。調過的 MySQL 參數（buffer pool、redo log、flush 策略）也要全部記進報告——這些會大幅影響絕對耗時，讀報告的人必須知道。

實務上我會要求：所有調參都用 SET GLOBAL 動態設定，不要改 my.cnf，這樣 docker compose restart db 就能全部還原，不會留下污染後續開發的環境。

長任務的工程問題

這類任務有一個 coding agent 日常任務不會遇到的問題：單一指令跑一小時以上。

  • session 中斷風險：跑 1 小時 55 分的 ALTER，中間 agent session 掉線或被中斷，整個情境就白跑。長指令要放在 tmux/nohup 裡跑並導出到 log 檔，agent 只負責輪詢 log，而不是自己 hold 住那個前景行程。
  • 邊跑邊寫：要求它每完成一個情境就把結果寫進報告檔，而不是全部跑完再一次產出。中途出事至少還留著前面的數據。
  • 耗時本身就是數據：所有指令都要記開始/結束時間戳，不要只留「完成了」。

意外收穫多半來自「路上發現」

最後報告裡有個附錄，記了三件不在測試計畫內的事：KILL 大交易的 rollback 代價、secondary index 對灌資料的放大效應、外接碟的 fsync 延遲才是真瓶頸。

這三件事都是灌測試資料的時候撞到的——原本只是準備工作，結果自己成了結論。其中 redo log 那個（預設 100MB 時 insert 掉到 70 筆/秒，調到 4GB 後 1,500 筆/秒）對日常開發的影響，甚至比某些正式測試項目還大。

所以我現在會固定加一句要求：把過程中遇到的異常、繞路、和「原本以為是雜訊結果不是」的東西也記下來。 準備階段的意外，資訊量常常比計畫內的測項高，因為那是你完全沒預期的部分。

哪些部分不能交給 agent

這輪下來，有三件事是我 review 時才處理、agent 不會自己做對的：

  1. 判斷數字能不能外推。 這台機器跑在外接 USB SSD 上，fsync 延遲是內建 NVMe 的 20 倍，絕對耗時比正常環境難看得多。報告必須明講「可外推的是量級與鎖行為，不是絕對秒數」——這個界線是人劃的，agent 只會忠實報出它量到的數字。
  2. 決定要不要動 production。 報告裡有幾個延伸推論（例如「drop 過 FULLTEXT 的表可能已經拿不回 INSTANT」），那是需要在 staging 驗證後才能排程處理的事，不是報告寫了就去做。
  3. 決定要測什麼、不測什麼。 有個情境（加第二個 FULLTEXT）評估後跳過了：又是兩小時級，而且 production 已經不用 FULLTEXT，投報率太低。這種取捨要人來下。

一句話總結分工：agent 負責舉證，人負責判決。 這跟我之前做大規模 dead code 清理時的結論是一樣的——AI 產出的不該是「答案」，而是「一份可以被驗證的證據」。
