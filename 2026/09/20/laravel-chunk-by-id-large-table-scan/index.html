大表全量掃描：從 chunk() 到 chunkByIdDesc()

一支要掃過五十萬筆資料的 backfill 指令，用 Laravel 的 chunk() 寫，跑到第 40 頁就開始每頁等 23 秒，全量推估要 6 小時。換成 chunkById() 之後全量 85 秒，快 180 倍。這篇談的不是「keyset 比 offset 快」這個老生常談，而是為什麼會有斷崖：MySQL 的查詢計畫在某個掃描深度會整個翻轉，從此每一頁都重做一次全結果集排序。最後還有一個與效能無關的收尾——為什麼掃描方向最後選了降冪。

重點摘要

一支 backfill 指令要掃過整張大表回填 filter metadata。原本用 chunk()（offset 分頁），在大表上退化到不可用；改成 chunkById()（keyset 分頁）後成本變平坦；最後改成 chunkByIdDesc()——吞吐量同量級，但先修最新的資料。

同樣掃過前 30,000 筆（本地實測，53 萬筆符合條件的資料）：

寫法 耗時 相對
chunk() — offset 分頁 629.8 s 基準
chunkById() — keyset 升冪 3.5 s 快 180×
chunkByIdDesc() — keyset 降冪 3.4 s 快 187×

全量掃完 53 萬筆：

寫法 耗時
chunk() 推估 ≥ 370 分鐘（6.2 小時）
chunkById() 85.1 s
chunkByIdDesc() 83.2 s

上表是單次執行的實測值。重跑的絕對數字會有明顯變異（offset 那欄兩次執行差 1.6 倍），但倍差穩定在 180–187×、斷崖位置固定、keyset 恆為平坦。引用時請引用量級與倍差，理由見後面「重跑的變異」。

一次 filter 功能改版新增了五個 metadata 欄位，還修正了兩個數值欄位的型別。這些都要對既有資料做一次全量回填，掃描條件大致是：

當時的寫法是 ->orderBy('id')->chunk(500, ...)。開發期間就發現：指令跑到兩萬多筆之後，進度條幾乎停住，每頁要等 5–6 秒且持續惡化。

Offset 分頁為什麼會崩潰

chunk() 產生的 SQL 是這樣的：

OFFSET 25000 不是「跳到第 25000 筆」——資料庫沒有辦法直接跳。它必須產生前 25,000 筆結果，然後把它們丟掉，再回傳接下來的 500 筆。第 N 頁要處理 N × 500 筆，整個掃描的總成本是 O(n²)。

但實際量測顯示，真正的行為比 O(n²) 更糟，而且有個斷崖。

實測：每頁耗時 vs 掃描深度

只取 id 欄位（隔離出純分頁成本），每個深度量 3 次取中位數：

掃描深度 LIMIT 500 OFFSET n keyset 升冪 keyset 降冪 倍差
0 6.0 ms 5.8 ms 0.6 ms 1×
10,000 46.9 ms 6.6 ms 7.2 ms 7×
25,000 2,415.2 ms 9.9 ms 8.0 ms 245×
50,000 2,650.9 ms 13.7 ms 8.5 ms 194×
100,000 2,573.9 ms 9.7 ms 10.2 ms 264×
200,000 2,260.5 ms 9.2 ms 7.6 ms 247×
400,000 2,453.3 ms 9.7 ms 8.3 ms 254×

注意成本不是平滑上升，而是在 10,000 到 25,000 之間跳崖 50 倍然後持平。這代表發生的不只是「多掃幾筆」。

根因：查詢計畫在深度門檻翻轉

EXPLAIN 同一條 query 在不同 offset 下：

兩個截然不同的執行模式：

  • 淺頁（offset < 門檻）：type=index key=PRIMARY——沿著主鍵順序走，讀 offset + limit 筆就停，不需要排序。rows 隨 offset 線性成長（1,000 → 21,000）。成本線性上升，總掃描 O(n²)。
  • 深頁（offset ≥ 門檻）：優化器判斷「沿主鍵走 25,000 筆」比「用 status 索引過濾後排序」還貴，於是翻轉計畫——改用 status 索引撈出全部 163,027 筆符合條件的 row，然後 Using filesort 對整組結果排序，最後才取那 500 筆。

第二種模式的每頁成本與 offset 無關（所以持平），但它是每一頁都重做一次全結果集排序。掃完 1,063 頁 = 排序 16 萬筆資料 1,063 次。

  • keyset：type=range key=PRIMARY，主鍵範圍掃描，沒有 filesort，且範圍上界由 LIMIT 決定——不論掃到多深，實際讀取都只有那 500 筆。

rows=163,027 是優化器的估計上限，不是實際讀取量。keyset 那列的 type=range + 無 filesort 才是重點。

加上真實工作負載後差距更大

上表只 SELECT id。真實指令是 SELECT * 加上兩個 eager load，filesort 要排的是完整資料列而不是單一欄位，斷崖更早、更陡。完整重跑三種寫法（batch=500，callback 內不做任何實際工作，只量分頁成本）：

量測方法與數字

環境

  • 本地 Docker（macOS），MySQL 容器，符合掃描條件者 531,229 筆
  • batch size 500 → 共 1,063 頁
  • callback 內不做任何實際的寫入工作——每頁的處理成本三種寫法完全相同，刻意排除以隔離分頁本身的成本
  • query 與 eager load 與正式指令完全一致

重跑的變異（執行 B）

同一台機器、同一份資料、同一支腳本，隔一段時間再跑一次：

指標 執行 A 執行 B
chunk() 前 60 頁 629.8 s 384.2 s
chunkById() 全量 85.1 s 82.1 s
chunkByIdDesc() 全量 83.2 s 58.5 s
同工作量倍差（前 30,000 筆） 187× 180×
尾段每頁均值 21.5 s 15.8 s
全量推估（下界） 370 分鐘 270 分鐘
最新 50,000 筆修復完成於（降冪） 5.1 s 3.7 s
斷崖位置 第 30–40 頁之間 第 30–40 頁之間

offset 的絕對數字在兩次執行間差了 1.6 倍（629.8 s vs 384.2 s），keyset 也有差異。這來自 buffer pool 冷熱、背景 worker 負載與容器資源競爭——這支腳本並沒有隔離這些變因。

⚠️ 特別注意 chunkByIdDesc() 那一列（83.2 s → 58.5 s）：腳本是依序跑三種策略的，降冪永遠排在升冪之後，吃得到已經被暖起來的 buffer pool。不要把它讀成「降冪比升冪快」——理由見下一節。

但結論完全不受影響，因為真正穩定的是結構性指標：

  • 斷崖固定落在第 30–40 頁之間（兩次都是從 ~230 ms 跳到 6,800–23,800 ms）
  • 倍差穩定在 180–187×
  • keyset 每頁成本與深度無關（兩次都在數十毫秒量級，第 1,063 頁不比第 1 頁貴）
  • offset 全量推估都在數小時量級，keyset 都在一分半以內

引用本文數字時請引用量級與倍差，不要引用小數點。

與 production 觀測的對照

更早之前在一個約 16 萬筆的資料集上，曾觀測到「offset 兩萬多筆處每頁 5–6 秒且持續上升」。本文的本地實測（53 萬筆、SELECT *）在相同深度量到 18–24 秒。兩者是同一個機制的不同規模：斷崖位置與絕對數字取決於資料量、索引統計與硬體，但「淺頁便宜 → 某個門檻翻轉計畫 → 深頁全部踩 filesort」的形狀一致。

不要把本文的絕對數字當成你自己系統的預期值，要記住的是形狀與量級。

為什麼最後改成降冪（chunkByIdDesc）

兩個 keyset 版本的全量耗時落在同一量級（升冪 82–85 s、降冪 59–83 s）。這點差距不能歸因於掃描方向——腳本是依序跑三種策略的，降冪永遠排在升冪之後，吃得到已經被暖起來的 buffer pool。兩者的執行計畫也完全相同（type=range key=PRIMARY、無 filesort、每頁實際讀取量都等於 batch size），沒有任何機制讓方向影響吞吐量。

所以這次改動的理由不是效能，是修復順序。

chunkById() 依 id 升冪掃描，也就是從最舊的資料開始修。在百萬級的索引上，全量 metadata 修復要跑上數小時，而使用者在搜尋結果裡看到的幾乎都是最新的資料——升冪掃描會讓「使用者實際看得到的那批資料」排在最後才修好。

量化這個差異（本地，最新的 50,000 筆需要多久被修到；兩次執行）：

掃描方向 最新 50,000 筆修復完成於
chunkByIdDesc() 3.7–5.1 s（前 100 頁）
chunkById() 82–85 s（整趟跑完才輪到）

本地是數秒 vs 一分多鐘；production 百萬級規模下，同樣的比例是數分鐘 vs 數小時。對一個修復性質的 backfill 來說，這是「使用者何時看到正確結果」的差異。

注意這個比例不受上面的量測變異影響：它不是兩種策略的效能比，而是同一趟掃描裡「最新資料排在最前面 vs 最後面」的結構性差異——降冪的分子恆為前 100 頁，升冪的分母恆為整趟。

這是個在總時間相同的前提下，重排工作順序來提早交付價值的改動。不是效能優化，不要跟上一段混為一談。

順帶清掉的：多餘的 orderBy('id')

chunkById() / chunkByIdDesc() 內部透過 forPageAfterId() 自己套用排序，外層再寫一次 orderBy('id') 只會讓 SQL 多出一個重複的 ORDER BY 子句。

陷阱：chunkById() 的游標欄位必須唯一

Keyset 分頁靠 WHERE id > $lastSeenId 前進，這個前提是游標欄位在結果集中唯一。用非唯一欄位當游標會靜默漏資料。

同一次 PR review 就抓到一個實例：

一個 parent 可以有多筆 child，parent_id 因此不唯一。當某頁的最後一筆與下一筆共用同一個 parent_id 時，WHERE parent_id > $last 會把後者整批跳過；distinct() 又讓每頁實際筆數與 chunk size 對不上，分頁邊界更難預期。

規則：chunkById() 的游標一律用主鍵。 需要去重就在 PHP 層做，不要靠 distinct() 配非唯一游標。

額外好處：keyset 對「掃描中修改資料」是安全的

前面談的都是效能。但 offset 分頁還有一個與效能無關的正確性問題，而且它比慢更危險——因為它不會報錯，只會安靜地漏掉資料。

問題的本質：offset 是「位置」，而位置會動

OFFSET 500 的意思是「在目前這條 query 的結果集裡，跳過前 500 筆」。關鍵在於，這個結果集是每一頁重新算一次的——chunk() 每翻一頁就重跑一次完整的 SELECT ... WHERE ... LIMIT 500 OFFSET n。

如果 callback 改動了會影響 WHERE 條件的欄位，下一頁重算出來的結果集就已經不是同一組資料了。offset 指向的位置還在原地，但資料整個往前滑了。

走一遍：1,000 筆資料，漏掉一半

假設要掃 status = 'active' 的 1,000 筆資料，每頁 500 筆，callback 的工作是處理完就把 status 改掉：

步驟 SQL 符合條件的總筆數 實際拿到
第 1 頁 LIMIT 500 OFFSET 0 1,000 原始的第 1–500 筆 ✅
callback 執行後 — 500（前 500 筆已變成 processed） —
第 2 頁 LIMIT 500 OFFSET 500 500 空的 ❌

第 2 頁下 OFFSET 500，但此刻結果集裡總共就只剩 500 筆（原本的第 501–1000 筆，現在排在位置 1–500）。跳過前 500 筆之後什麼都不剩，query 回傳空集合，chunk() 認定掃完了、正常結束。

一半的資料從頭到尾沒被碰過，而且指令的 exit code 是 0。 沒有例外、沒有警告、進度條還會漂亮地跑到底。

如果 callback 只改動部分 row，症狀會更難察覺：改掉 N 筆，後面的資料就往前位移 N 格，下一頁的 offset 會跳過 N 筆——漏掉的比例剛好等於你改動的比例，而且散布在整個資料集裡，肉眼對不出來。

反方向也會出事

如果 callback 讓更多 row 符合 WHERE 條件（例如把別的資料改成 active，或掃描期間有新資料寫入），位移方向相反：後面的 row 往後退，下一頁的 offset 會重複拿到已經處理過的資料。

對於非冪等的 callback（發通知、扣額度、寫入計數），重複處理的後果通常比漏掉更嚴重。

keyset 為什麼不受影響

chunkById() 記的是上次看到的那筆資料的 id，不是位置。不管結果集在這期間縮小、膨脹還是重排，「id > 1234」指向的永遠是同一個邊界。已處理過的資料從結果集裡消失，反而讓後續每一頁都更省事——這也是為什麼 keyset 配上「處理完就改狀態」的模式，效能會比純掃描更好。

順帶一提，Laravel 官方文件對 chunk() 也有同樣的警告，並直接建議在更新資料時改用 chunkById()。這不是什麼冷知識，但它藏在文件段落裡，很容易在趕工時略過。

規則：任何會在掃描過程中修改資料的批次作業，都必須用 chunkById()。 就算資料量小到 offset 的效能問題還沒浮現，正確性問題從第一頁就存在了。

收斂成六條規則

這次的結論最後寫進了專案的開發規範：

  1. 大表全量掃描一律用 chunkById() / chunkByIdDesc()，不要用 chunk() / offset() / paginate()。 Offset 分頁在超過某個深度後會讓查詢計畫翻轉成「每頁重做一次全結果集 filesort」，實測深頁單頁 18–73 秒，全量掃描不可行。
  2. chunkById() 的游標欄位必須唯一，一律用主鍵。 非唯一游標會在邊界值處靜默跳過整批資料；需要去重時在 PHP 層 ->unique()，不要用 distinct() 配非唯一游標。
  3. 不要在 chunkById() 外層再寫 orderBy()。 它會自己套用排序，外層只會產生重複的 ORDER BY。
  4. 修復性質的 backfill 用 chunkByIdDesc()。 總時間相同，但最新、使用者實際看得到的資料會先被修好。
  5. 會在掃描過程中修改資料的批次作業必須用 chunkById()。 Offset 分頁在 callback 改動影響 WHERE 條件的欄位時，結果集會位移導致跳過資料。
  6. 效能宣稱要附上量測方式。 至少要有「同樣工作量的 before/after」與量測環境；EXPLAIN 是判斷分頁退化的第一個工具，看 type 與 Extra 有沒有 Using filesort。

如果你想在自己的系統上驗證

三支腳本的設計思路，照著寫就能重現本文的三張表：

  1. 執行計畫比對（數秒）——同一條 query 套不同 offset 跑 EXPLAIN，看 type / key / Extra 在哪個深度翻轉。這是最快能確認「你的系統有沒有這個問題」的方法。
  2. 單頁延遲 vs 掃描深度（約 2 分鐘）——只 SELECT id，在 0 / 1 萬 / 2.5 萬 / 5 萬 / 10 萬 / 20 萬 / 40 萬各量 3 次取中位數，藉此隔離出分頁策略本身的成本。
  3. 端對端全量掃描（約 15 分鐘）——三種寫法各跑一次，chunk callback 刻意不做任何實際工作；chunk() 跑滿 60 頁就中止，讓它跑完全量並不實際。

⚠️ 這類腳本會掃過整張表數次。只在本地或 staging 跑，不要對 production 執行。

重跑時要對照的是形狀與量級（淺頁便宜 → 某個門檻翻轉計畫 → 深頁全部踩 filesort），不是絕對數字——那會隨資料量、索引統計與硬體而變。
