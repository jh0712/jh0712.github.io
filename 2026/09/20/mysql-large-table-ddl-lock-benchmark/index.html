MySQL 大表 DDL 實測：哪些操作會鎖表、哪些會讓你等一小時

有在對大表做 DDL 的人，大概都聽過 MySQL 的 Online DDL——官方文件有一張表，清楚列出每個操作支不支援 In Place、會不會重建表、允不允許並行 DML。問題是那張表講的是「這個操作能不能線上做」，不是「你這張表現在做會怎樣」。我們的 items 表就是在 production 上加欄位出過事，而可能的解釋有好幾個，每一個都只在特定條件下成立——缺的是在自家版本與資料量上量出來的數據。所以我用一張 100 萬筆、15GB 的複製表把情境逐一實測，得到一張可以在寫 migration 前直接查的對照表：同樣是加一個欄位，最快 0.8 秒，最慢默默跑 67 分鐘；同樣是加外鍵，兩種寫法差五千倍。

為什麼還要自己測一次

Online DDL 的基本盤

先對齊名詞。MySQL 從 5.6 開始提供 Online DDL，ALTER TABLE 有兩個可以指定的參數：

  • ALGORITHM：INSTANT（只改資料字典，8.0.12 起支援加欄位）／INPLACE（不複製整張表，但可能重建）／COPY（建一張 tmp table 整批複製過去）。
  • LOCK：NONE（讀寫都不擋）／SHARED（擋寫不擋讀）／EXCLUSIVE（讀寫全擋）。

哪些操作支援哪種組合，官方文件的 Online DDL Operations 列得很完整，該查的時候就去查。現在更快的做法是直接問 AI，通常也能得到方向正確的答案。

那為什麼還要測

因為官方表格和 AI 的答案，講的都是「這個操作在條件符合時的行為」，而那些條件寫在附註裡、或根本取決於你這張表的歷史狀態。 同一句 ADD COLUMN，實際會走哪條路徑取決於：

  • 表上有沒有 FULLTEXT index（有的話 INSTANT 和 INPLACE 都會被拒）
  • INSTANT 的 row version 額度還剩幾次（上限 64）
  • 你的 MySQL 是哪個小版本（AFTER xxx 在 8.0.28 前後行為不同）
  • 這張表過去有沒有被 drop 過 FULLTEXT（殘留物會讓 INSTANT 一直拿不回來）
  • 執行當下有沒有別人開著沒 commit 的交易

最後兩點尤其是 AI 不會主動提醒你的：一個從舊版本一路升上來、被改過很多次的 production 表，它的實際行為不等於同名新表的行為。 你問到的是「MySQL 8.0 的 ADD COLUMN 支援 INSTANT」，這句話沒錯，但你那張表可能剛好四個條件都不符合。

而最危險的地方在於——條件不符合時，MySQL 多數情況不會報錯，它會默默換一條更慢的路徑跑下去。 你以為是 0.8 秒的 migration，結果跑了 67 分鐘；你以為只是加個欄位，結果全程擋寫。

還有一層是 Online DDL 文件不會告訴你的：就算 LOCK=NONE 全程不擋讀寫，ALTER 開始和結束仍然要拿 exclusive metadata lock。 只要當下有一個沒 commit 的長交易，它就會卡在那裡，而排在它後面的所有查詢（包含純 SELECT）一起排隊——這跟你的 ALTER 快不快完全無關，卻是「migration 一跑全站掛」最常見的機制。

所以這次實驗的目的，不是重新驗證 MySQL 手冊，而是找出我們這套系統當下的實際規則：在我們的版本、我們的表結構、我們的資料量上，哪些操作安全、哪些會鎖、哪些會默默變慢。讓後面的人寫 migration 時有依據可查，降低出錯機率。

四條待驗證的「已知事項」

測試前，關於「什麼情況會鎖表」我們手上有四條說法：

  1. table 中如果有 fulltext index，建立新欄位會重建表
  2. metadata change 超過 64 次會需要重建表
  3. 有其他資料在寫入時，建欄位要等寫入結束
  4. 新欄位如果指定位置（AFTER xxx），會重建表

來源分別是事故檢討、網路文章與 AI 的回答——都是合理的來源，但共通點是各自的成立條件不同，而且都還沒有在我們自己的版本、自己的資料量上量測過。所以這次測試的第一原則是：把已知事項當成待驗證的假設，不是前提。

結果是三條成立（其中兩條比想像的更糟），一條已經過時——那條正好是「8.0.28 以前才成立」的典型：文章寫的時候沒錯，只是我們的版本早就跳過去了。

項目 值

版本相同這點很重要——INSTANT 的行為和 64 次上限的結論可以直接套用到 production。

但絕對耗時不要直接拿去用。這台機器的瓶頸是外接碟的 fsync 延遲（後面附錄會講），數字會比正常機器難看。可以外推的是量級與鎖行為：一個操作是「秒級」還是「小時級」、會不會擋寫，這兩件事跟磁碟快慢無關。

耗時分類沿用這次的定義：秒級（<2min）／久（2–5min）／很久（>5min）。

怎麼證明「有沒有擋寫」：探針

這是整份測試最關鍵的方法論。不要靠 processlist 目測，也不要靠「感覺卡住了」——開一個背景迴圈，每 0.5 秒對測試表寫一筆，記錄每筆的耗時。DDL 期間如果探針耗時從 0.01 秒暴衝到 700 秒，那就是被擋的直接證據。

同樣做一支讀取探針（點查 SELECT），就能分辨「擋寫但不擋讀」和「讀寫全擋」。這一對探針讓後面每個「是／否」欄位都有數據支撐，而不是推論。

四條已知事項的驗證結果：

已知事項 驗證結果
1. 有 FULLTEXT 時加欄位會重建表 ✅ 成立，而且更糟：INSTANT/INPLACE 都被拒，默默走 COPY（重建＋全程擋寫）。而且 drop FULLTEXT 後 INSTANT 不會自己復活
2. metadata change 超過 64 次需要重建表 ✅ 成立，而且更危險：不是報錯，是普通 ADD COLUMN 默默變成 67 分鐘重建
3. 有其他寫入時建欄位要等 ✅ 成立，而且更嚴重：不只 DDL 要等，DDL 後面的所有查詢（含純 SELECT）一起排隊
4. 指定位置（AFTER xxx）會重建表 ❌ 不成立（8.0.29+）：AFTER 照樣走 INSTANT，0.1 秒完成

下面挑五個最值得記住的場景細講。

場景一：INSTANT 的 64 次額度用完，不報錯，默默跑 67 分鐘

MySQL 8.0 的 INSTANT ADD COLUMN 之所以能 0.8 秒完成 100 萬筆的表，是因為它不動資料，只在資料字典記一個新的 row version。代價是每張表最多 64 個 row version，每次 INSTANT ADD/DROP COLUMN 消耗一次，只有全表重建才會歸零。

真正的陷阱是不寫 algorithm——也就是 Laravel migration 的預設寫法：

這 67 分鐘不擋寫（7,539 筆探針全過，最慢 1.24s），服務是活的。但 migration 會掛 67 分鐘，而部署 pipeline 通常有 timeout——中途被 SIGHUP 砍掉的風險比鎖表本身更實際。

所以結論很簡單：加欄位就明確寫 ALGORITHM=INSTANT。Laravel 裡用 DB::statement 就好。它的價值不在於變快，而在於不能 INSTANT 的時候會立刻報錯，而不是默默跑一小時。

這就是我們先前那次事故的根因。

然後是最反直覺的一段：drop 掉 FULLTEXT 之後，INSTANT 並沒有復活。

原因是曾有 FULLTEXT 的表會殘留隱藏欄 FTS_DOC_ID 和資料字典裡的 FTS 輔助表項目。要再做一次全表重建（ALTER TABLE ... ENGINE=InnoDB）才會清掉——實測又是 4,143 秒（69 分鐘），雖然不擋寫。重建後 INSTANT 才真正恢復（0.39s 成功）。

FULLTEXT 的完整生命週期成本，1M 筆 / 15GB 實測：

加第一個 FT = 1h55m 擋寫 → 之後每次加欄位 = 強制 COPY 擋寫 → drop FT = 0.24s（唯一便宜的一步）→ 還要再花 69 分鐘 rebuild 才拿回 INSTANT。

結論：不要在大表上加 FULLTEXT。 需要全文檢索就開伴表（我們改用 item_search_index 的模式）。

另外有個延伸的行動項：**任何 drop 過 FULLTEXT 的表，如果沒做過重建，之後所有「普通 ADD COLUMN」都可能在默默走 INPLACE 重建。

場景三：型別變更 = COPY = 全程擋寫

12 分鐘的 watchdog 到期時仍停在 copy to tmp table，只能手動 KILL。寫入探針卡了 723 秒——從 ALTER 開始到被砍，一筆 INSERT 都沒進去；砍掉後瞬間恢復。

varchar→text、int→bigint、改 charset/collation——這一整類都是同一個下場：必走 COPY、全程擋寫、耗時以小時計。這是大表上最危險的一類 migration。

要做就走「加新欄位 → 背景 backfill → 切換讀寫 → 擇期刪舊欄」的流程。

順帶一提：KILL 一個進行中的 COPY ALTER 是安全的，只是丟棄 tmp table，原表不動、恢復很快。（但 KILL 一個大的 DML 交易完全不是這回事，見附錄。）

場景四：一個沒 commit 的 SELECT，就能讓全站排隊

這是最該記住的一個機制，因為它跟你的 ALTER 快不快完全無關。

還有一個容易忽略的：CREATE TABLE 帶 FK 指向大表時，一樣要拿父表的 MDL。實測在父表有 30 秒長交易時，建一張新的空表卡了 28 秒——而且卡住期間一樣會觸發場景四的排隊連坐。建新表不等於安全操作。

給 Laravel Migration 的八條建議

  1. 加欄位明確寫 ALGORITHM=INSTANT。能成功就是 0.x 秒；不能就立刻報錯，而不是默默跑一小時。報錯了再判斷是額度用完還是 FTS 殘留。
  2. 跑任何大表 DDL 前先 SET SESSION lock_wait_timeout=5，並檢查 information_schema.innodb_trx 有沒有長交易。
  3. 型別變更／改 charset = COPY = 擋寫數小時，改走「新欄位 + backfill + 切換」。
  4. 絕不在大表上加 FULLTEXT，需要全文檢索走伴表。
  5. 加 FK 用 foreign_key_checks=0 + ALGORITHM=INPLACE, LOCK=NONE，但要自己先驗孤兒資料。
  6. 監控 INSTANT 額度，接近 64 就規劃一次 off-peak 重建。
  7. 多個欄位變更合併成同一個 ALTER：只耗一次額度、一次 MDL。
  8. KILL 之前先想清楚：KILL ALTER ... COPY 安全，KILL 大交易不安全（見下）。

附錄：灌資料過程的三個意外收穫

這三件事不在原本的測試計畫裡，是建測試資料時撞到的。

KILL 大交易的代價遠超預期

seed 過程中兩個各插入約 152k 筆（未提交）的交易被 KILL，rollback 花了 30 分鐘以上——undo 要逐筆反向刪除 PK 加 17 個 index entry，全是隨機 IO，而且單執行緒。

教訓：production 上 migration/backfill「卡住就 kill」不是免費的，回滾時間 ≥ 已執行時間，而且期間鎖照樣持有。這也是 backfill 一定要用 chunkById() 小批提交的另一個理由：已提交的批次不需要回滾。

Secondary index 對大量寫入的放大效應

同樣 45k 筆一塊的 INSERT：

條件 每塊耗時
17 個 secondary index 齊備 357s
只留 PK（灌完再建 index） 16s（表小時）～ 280s（表大後）
只留 PK + 關 doublewrite/降 flush 148–192s

「先卸 index、灌完重建」依然是數量級的差異——畢竟重建 17 個 index 也才 320 秒。

外接碟跑 DB 的真瓶頸是 fsync 延遲，不是頻寬

標稱 1050MB/s 的 USB SSD，循序寫實測 450MB/s 沒問題，但 16KB dsync 寫入只有 776KB/s（每次 flush 約 21ms，內建 NVMe 通常 <1ms）。InnoDB 的 redo、doublewrite、頁刷全是 fsync 密集操作，有效吞吐直接掉到個位數 MB/s。

另外 innodb_redo_log_capacity 預設只有 100MB，大量寫入時 checkpoint 壓力讓 insert 掉到約 70 筆/秒；調到 4GB 後同樣負載約 1,500 筆/秒，20 倍差距。

本地要跑大資料量測試，innodb_flush_log_at_trx_commit=0 + innodb_doublewrite=DETECT_ONLY（僅限 dev！）可以救回一倍以上。
