讓 Claude Code 把工作丟給 Codex：plugin 串接實戰與踩雷筆記

OpenAI 官方出了一個 Claude Code plugin，可以在同一個 session 裡把 code review、debug、甚至整包任務丟給 Codex 執行。我實際串起來跑了幾輪，安裝本身十分鐘搞定，真正該注意的是後面那些文件沒寫清楚的事：派工時 Codex 會繞過 Claude Code 的權限確認直接改你的檔案、它在 macOS sandbox 下跑不了 Docker、以及 plugin 的「丟出去等結果」模式在什麼情境下根本不夠用。這篇記錄完整流程與這幾個踩雷點。

環境：macOS / Claude Code / Codex CLI 0.154.0。

為什麼要多請一個「別家的 AI 同事」

這個 plugin 做的事情很單純：讓 Claude Code 把工作丟給 Codex（GPT-5.x / GPT-6）去做，再把結果帶回來。

價值不在於「多一個模型」這件事本身，而在於三個具體的好處：

  • 盲點不重疊。同一個模型審自己寫的 code，會傾向認可自己的推理路徑——它記得自己「剛才為什麼這樣寫」，那個理由會繼續說服它。Codex 對你的 diff 沒有這種記憶包袱，看到的是純粹的結果。
  • 兩個獨立的額度池。Claude 這邊額度吃緊時，繁重的工作可以丟給 Codex，不必停下來等額度回補。
  • 可以按專長分工。不同 model 擅長的事情不一樣——規劃、效能優化、UI 畫面的細膩度，各家表現有差，可以按任務性質挑。

一、安裝與健康檢查

四行指令：

/codex:setup 成功的輸出長這樣：

項目 預期值
ready true
node / npm 有版本號即可
codex codex-cli 0.154.0; advanced runtime available
auth ChatGPT login active for <你的帳號>，verified: true
sessionRuntime direct（正常，見下方說明）
reviewGateEnabled false（預設關閉，建議先維持）

如果 codex.available = false 但 npm 可用，補裝 Codex CLI：

若顯示未登入，在 Claude Code 的輸入框打 !codex login 即可。

sessionRuntime: direct 不是錯誤。 Codex companion 不會在 setup 階段就起一個常駐 process，而是等第一次 review/task 才 spawn。這讓 /codex:setup 是純健康檢查、沒有副作用——對同時開多個 parallel session 的工作流特別重要，否則每個 tab 都會多掛一個閒置 runtime。

二、指令總覽

主要功能

指令 用途
/codex:review 用 Codex 審查目前的 git 變更
/codex:adversarial-review 更嚴謹的版本：不只挑 bug，還質疑設計決策與假設
/codex:rescue <任務> 派工：調查問題 / 修 bug / 寫功能（會改檔案）
/codex:transfer 把目前 Claude session 轉成 Codex thread，給你 codex resume <id>

背景工作管理

指令 用途
/codex:status 看有哪些 Codex 工作在跑 / 跑完
/codex:result <job-id> 取回某個工作的完整結果
/codex:cancel [job-id] 取消背景工作

常用參數

--effort 和 --model 會被當成 routing control 剝離，不會混進給 Codex 讀的 prompt。所以可以很自然地寫 /codex:rescue --effort high 為什麼 date widget 填不進去，不用擔心參數被當成需求描述的一部分。

三、預設 model 與計費：錢從哪裡扣

預設 model 取決於你的 ~/.codex/config.toml

Plugin 本身沒有寫死任何預設 model。解析鏈是三層：

以我本機的設定為例：

設定 值
model gpt-6-astra
model_reasoning_effort low
service_tier default

⚠️ 注意 model_reasoning_effort = "low"。 派複雜任務時務必明確覆寫 --effort high，否則 Codex 會用低思考預算去處理需要深度推理的問題，交出一份看起來完成、實際上很淺的結果。

副作用提醒：改 ~/.codex/config.toml 會同時影響「直接用 Codex CLI」和「透過 Claude Code 派工」兩條路徑。想讓派工用更強的設定，請在指令上加 flag，不要去動 config。

Token 走 ChatGPT 訂閱，不是 API call

/codex:setup 的輸出裡有兩個關鍵欄位：

  • authMethod: "chatgpt" → 用 ChatGPT 帳號登入（~/.codex/auth.json），不是 API key
  • provider: null → 沒設定第三方 API provider

也就是說，消耗的是 ChatGPT 方案的 Codex 額度，不會產生 OpenAI API 帳單。

動作 算誰的額度
Claude Code 自己做事 Anthropic
/codex:review、/codex:rescue ChatGPT Codex 額度

四、派工前必讀：權限與 sandbox

這節是整篇最重要的部分。

Codex 改檔案不會問你

/codex:rescue 預設帶 --write。翻 plugin 原始碼：

workspace-write + approvalPolicy: "never"，意思是 Codex 會在你的 repo 裡直接寫檔，不經過 Claude Code 的權限確認。

原因是 Codex 在子行程裡跑自己的工具迴圈，那些寫入對 Claude Code 的權限系統完全不可見。所以派工這個動作，本質上等於暫時放棄逐步審核。

防線要建在 git，不是權限提示

既然權限提示指望不上，防線就得換一層：

  1. 先開 branch 再派工（本來的開發流程就是 create issue → create branch，這裡要確實執行）
  2. 或是開 worktree，讓 Codex 在隔離環境動手
  3. 派完工一定 git diff 檢查

跨分支記得加 --fresh

--resume-last 是 per-repo 的狀態。「continue / keep going / apply the top fix」這類詞會自動接續舊 thread。如果中間切過分支，Codex 記得的會是舊 context——這時要明確加 --fresh。

五、已知限制：Codex 跑不了 Docker

實測結論：派工給 Codex 時，不要把 docker 指令當成它會執行的驗證步驟。

實際發生的狀況是：Codex 改完碼，回報「Docker socket 權限遭拒、測試未啟動、未 commit」，交付就停在半路。

原因

macOS Seatbelt 把 unix socket connect 當成 network-outbound 擋掉了。本機的 daemon socket 是 OrbStack 的 ~/.orbstack/run/docker.sock，位置在 workspace 之外：

而 plugin 把 sandbox 等級寫死在 codex-companion.mjs:491，沒有參數能傳遞 socket 權限。

試過無效的方法

嘗試 結果
預設 workspace-write ❌ 拒絕
-c sandbox_workspace_write.writable_roots=[...] ❌ 無效（socket connect 不是檔案寫入）
-c sandbox_workspace_write.network_access=true ❌ 無效（該開關管 TCP/DNS，碰不到 AF_UNIX）
codex sandbox --allow-unix-socket ~/.orbstack/run ✅ 成功，但 app-server 路徑吃不到

常見分工

另外，派工 prompt 裡要明確要求 Codex「回報跑了什麼、什麼被跳過」，否則很容易誤以為它驗證過了。

註：Codex CLI 0.154 有 [permissions] named profile（schema 含 network.unix_sockets）加上 default_permissions 與 -P，理論上可以讓 app-server 路徑吃到 socket 權限，但我還沒驗證過。在驗證之前建議維持現行分工，不要去改 ~/.codex/config.toml。另外提醒：docker socket 等於 host root，開放前要想清楚。

六、Review Gate（建議保持關閉）

開啟後，每次 Claude 要結束回合前，強制先跑一次 Codex review 才准收工。

建議先保持關閉：全域強制 gate 會讓每次收尾都多等一次外部模型呼叫，成本和延遲都是固定支出。比較合理的用法是在改動風險高的分支臨時打開。

七、建議工作流

A. Code review 雙保險

B. 大型機械性工作丟背景

C. 不值得派工的

  • 小改動、Claude 當場就能做完的事
  • agent 定義裡其實講明了：「Do not grab simple asks that the main Claude thread can finish quickly on its own」

八、Plugin 之外：讓 Codex 有自己的 session

Plugin 的派工本質是 subagent 模式：丟出去、等結果。/codex:rescue 一旦送出，你就看不到中間過程，不能在它走偏的當下喊停，也不能在做到一半時補一句「這裡改用另一個做法」。要調整只能整包重派。

/codex:transfer 比較接近互動，但它搬的是整個 Claude session，顆粒度太粗——你想交出去的通常只是「一個任務」，不是整段對話。

做法：用 cmux / tmux 開一個真正的 Codex session

不透過 plugin，而是讓 Claude 幫你開一個新的終端 session、在裡面跑起 Codex，再把任務送進去：

用 tmux 或其他 TUI 工具也是同樣的思路，差別只在終端管理工具。

好處一：Claude 幫你做 prompt enhancement

你丟給 Claude 的往往只是一句話，或一段粗略的總結。但 Claude 手上有這個 session 的完整脈絡——剛看過哪些檔案、踩過哪些坑、專案的架構規範——它可以把這些細節填進要送給 Codex 的 prompt 再送出去。

這正好補上下一節會提到的問題：codex-rescue agent 是刻意設計成不加工的轉發層，prompt 品質要你自己負責。走 cmux 這條路，等於把那層被省掉的加工用另一種方式補回來。

好處二：可以進去監工，而不只是等結果

session 是活的，你隨時可以切進那個 tab：

  • 看它現在在讀什麼、跑什麼指令，而不是等一份事後報告
  • 方向不對就當場打斷、補指示，不用整包重派
  • 需要接手時直接在同一個 thread 繼續談，上下文都還在

對於需要多輪來回的任務——設計方向未定、規格會在過程中微調——這個差別直接決定了派工能不能用。

怎麼選

情況 用哪個
任務明確、一次到位（機械性重構、補測試） /codex:rescue --background
只想要第二雙眼睛審 code /codex:review
方向未定、需要中途調整或監工 cmux / tmux 開獨立 session
想把整段對話都交給 Codex 接手 /codex:transfer

一句話總結：plugin 適合「交代得清楚的工作」，獨立 session 適合「需要邊做邊談的工作」。

九、設計細節備忘

翻 plugin 原始碼時注意到幾個刻意的設計，理解它們有助於判斷什麼時候該用、什麼時候不該用：

  • 大部分指令有 disable-model-invocation: true——Claude 不能自作主張呼叫，只有你手動打才會觸發。唯一的例外是 /codex:rescue。這是刻意的成本控管。
  • codex-rescue agent 是刻意設計成「什麼都不做」的轉發層——model: sonnet、只給 Bash 工具、規則明令禁止它讀檔案或自己推理。目的是避免雙重付費：你要的是 Codex 的判斷，不是再多墊一層 Claude 的加工。代價是派工 prompt 的品質要靠你自己寫清楚，中間沒有人幫你補上下文。
  • /codex:review 讀的是 git state，不是對話記憶——參數是 --base <ref> / --scope working-tree|branch。改動必須先落到檔案（不用 commit，working tree 就行）才有東西可看。

小結

安裝很簡單，難的是知道它的邊界在哪：

  1. 派工會繞過權限確認直接改檔，防線建在 branch 和 git diff
  2. Codex 在 sandbox 裡跑不了 Docker，驗證這一段留給 Claude
  3. model_reasoning_effort 預設可能很低，重要任務明確加 --effort high
  4. 需要邊做邊談的任務，開獨立 session 比用 plugin 派工划算

這套組合跟之前實測 ultracode 多 agent workflow的結論其實方向一致：工具能幫你把工作發出去，但「發出去之後怎麼驗收」才是決定它有沒有用的地方。
